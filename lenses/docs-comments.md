# Lens: Docs & comments accuracy

## Mission
Protect readers from text that lies. Once this change merges, a comment, docstring, README section, help string or changelog entry that contradicts the code will be trusted by the next maintainer or user — they will write a wrong caller, run a wrong command, or "fix" correct code to match a wrong comment. A finding from this lens costs the author a one-minute edit now and saves someone else hours later. Every finding here is a pair: a sentence someone will read, and the code that makes it false. This lens does not ask for more documentation and does not comment on wording. Use `category: "docs-comments"`.

## Where to look first
Work from code changes outward to the prose that describes them, then from prose changes back to the code.

1. List the facts that changed in your assigned files: signatures (params added, removed, renamed, reordered, retyped), return values and thrown errors, defaults, constants carrying units or limits, CLI flags and subcommands, env vars, config keys, routes, renamed or deleted files and symbols. In an incremental review only facts changed in `range.diff` count.
2. For each fact, visit its doc surfaces in the code directory (it holds the new version, so any hit is text that survives the change): the doc block directly above it; inline comments inside and just above the changed block; then prose elsewhere — `*.md`, `docs/`, `examples/`, help/usage strings, `.env.example`, sample configs, OpenAPI/GraphQL/proto descriptions.
3. Search by name, not by number. For anything renamed or removed, search for the OLD name verbatim (flag, env var, key, function, file path) — this is the highest-yield move in the lens. For a changed value, searching for "3" or "30" drowns you in noise; search for the constant's or option's name and read the prose around each hit.
4. For hunks that add or edit prose (comments, docstrings, README, CHANGELOG), pull out each factual claim — names, values, units, ordering, conditions, guarantees — and check it against the code at the new version.
5. Read "Claims to check" in `brief.md` (or the description in `context.json` when there is no brief) for claims about documentation only.
6. Spend little time on: refactors with no nearby comments, tests and fixtures, generated or vendored files, lockfiles, licence headers, old CHANGELOG entries, and directives written in comment syntax (`//go:build`, `# type: ignore`, `// eslint-disable`, `//nolint`) — those are code, and CI owns them.

## What to hunt for
- **Param/return/throws docs out of step with a changed signature** — JSDoc `@param/@returns/@throws`, Python `Args:/Raises:`, Javadoc/KDoc `@throws`, C# `<param name=…>`, Rust `# Errors`/`# Panics`, Go "Foo returns …". A documented parameter that no longer exists, a renamed one still under its old name, a changed type or nullability. The same applies to a new function whose doc block was pasted from a sibling and still names the sibling's parameters. Callers code against the hover text, not the body. Confirm: compare the new signature and every `return`/`throw`/`raise` in the body against the doc block, name by name.
- **Behaviour sentence contradicts the logic** — "returns null if not found" but it now throws; "sorted ascending" after the sort was removed or reversed; "inclusive" next to `<`; "case-insensitive" after the lowercasing was deleted. Confirm by reading the entire function plus any wrapper or decorator that could still supply the behaviour.
- **Unchanged comment made false by the code changed beneath it** — `// skip inactive users` above a filter that now also skips trial users; "keep in sync with X" where only one side changed. These live longest because no diff line highlights them. Confirm: read 10-15 lines either side of every changed hunk in the full file, not in the patch.
- **Numbers, units and defaults duplicated in prose** — "retries 3 times", "timeout in seconds", "max 10 MB", "defaults to `info`" beside a constant, default argument or schema default this change edited. Unit mistakes become 1000x errors in caller code. Confirm: open the definition and how it is consumed (`sleep(t)` vs `sleep(t / 1000)`); check help, log and error strings that embed the same number.
- **References to things that no longer exist** — `see parseConfig()`, `{@link OldClass}`, Sphinx `:func:` roles, `@deprecated use X instead`, README paths to moved files, links to renamed anchors, where this change renamed, moved or deleted the target. Confirm: search for the target's definition at the new version; zero hits makes the finding.
- **User-facing reference docs still teaching old behaviour** — README usage, `--help` strings (argparse, click, clap, cobra, commander, picocli), man pages, config tables, `.env.example`, sample `config.yaml`, Helm `values.yaml` comments, OpenAPI `description`/`default`/`required`. The change renamed or removed a flag, env var, key or endpoint, or changed its default. Confirm: open the option's definition site (parser or schema, not the handler) and look for a backwards-compatible alias before claiming the old name is dead.
- **Examples that fail when pasted** — README snippets, docstring examples, `examples/` files and quick-start commands that call the old signature, import from a moved path, pass a removed option or use a renamed subcommand. This is the first thing a new user runs. Confirm: resolve each import, function name, keyword argument and flag in the snippet against the new code; only the parts this change touched are in scope.
- **Guarantees the code no longer keeps** — "never returns null", "always returns a list", "does not modify its argument", "idempotent", "validates input", where either the sentence is added by this change or this change added the line that breaks it. Callers drop their own guards because of these words. Confirm: quote the one line that breaks it (a new `return None` path, an in-place `.sort()`, a second insert with no existence check). "Thread-safe" and complexity claims usually need an argument rather than a quote, so leave them to the concurrency and performance lenses unless the break is a single unmistakable line, such as a lock acquisition this change deleted.
- **New CHANGELOG, release-note or migration-guide entry that misdescribes the change** — says "X now defaults to true" while the diff sets false; says "no breaking changes" while a documented flag is removed with no alias; names a symbol that shipped under another name. Operators read these before upgrading. Judge only the entry this change adds, against the diff itself.
- **TODO/FIXME/HACK that this change made false** — the change implements what the TODO asks and leaves it in place; removes a workaround but leaves "workaround for #123" on what remains; deletes X but leaves "TODO: remove once X is gone". A stale TODO invites someone to redo or undo finished work. In scope only when the marker sits inside or within about five lines of a changed hunk, or names a symbol this change touched. Confirm by pointing at the changed lines that do what the TODO asks; "probably done" is not enough. TODOs the change adds belong to the maintainability lens.
- **PR description claims documentation the diff lacks** — "updated the README", "documented the new flag", "added a migration guide", where no such doc changed or the changed doc never mentions the thing. Reviewers skip checking docs because of these words, and with squash-merge they become permanent history. Confirm by opening the doc in the code directory and searching it for the thing claimed; the file index alone is not enough in an incremental review, where an earlier commit may have done it. Claims about behaviour ("adds backoff") belong to the correctness lens. Report only when the code the claim is about (the flag's definition, the new function) is in your shard, so parallel shards do not each raise it, and anchor there; with no fitting changed line, write one sentence in `notes` instead.
- **Docs that steer users into danger (the red case)** — help text still says "prompts before deleting" after this change removed the prompt; upgrade notes added here call a migration reversible while its down step drops a populated column; docs say a value is "redacted in logs" or "certificates are verified by default" after this change logs it raw or flips the default. Confirm the destructive or exposing path end to end in code (the delete is reached with no prompt; the log call prints the raw value) before using `red`.

## Confirm before you report
1. **Put the two quotes side by side.** Copy the exact doc sentence (path:line) and the exact contradicting code (path:line) into `evidence`. For a dead reference or an undelivered doc claim the second quote is the search you ran and its zero hits. If the contradiction is not visible from the pair alone, without an argument in between, it is not a finding for this lens.
2. **Quote the text from the code directory, not from a patch.** The fix may have landed in a file outside your shard or, in an incremental review, in an earlier commit. If the doc already reads correctly at the new version, there is nothing to report. Also check the passage describes the current version rather than history.
3. **Rule out "true at another layer".** Read the whole function and one hop out: wrapper, decorator, middleware, base class, database default or `ORDER BY`, parser alias, deprecated-name shim. Docs often describe the contract as the caller sees it, and another layer fulfils it.
4. **Prove this change caused it.** The removed (`-`) lines of the patch should show the old name, value or behaviour that the text matched; failing that, read `git show <base>:<path>`, where `<base>` is `range.full_from` in `context.json`. True before and false now is in scope. Already false before, with neither the text nor the fact it describes touched, is pre-existing — drop it. Text this change itself adds or edits is always in scope.
5. **Choose the anchor by what changed.** Wrong text on a changed line: anchor there, and if you are certain of the corrected wording put it in `suggestion` (replacement lines only, keeping comment markers and indentation). Unchanged text falsified by changed code: anchor on the changed code line that falsifies it, give the stale text's path:line in `body` and `evidence`, and leave `suggestion` empty because the fix is elsewhere.
6. **One finding per stale fact, not per hit.** If the old flag name survives in README.md, docs/cli.md and `.env.example`, that is one finding listing all three locations in `body`. The author fixes them in one pass, and separate findings would crowd out other defects.
7. **Write `scenario` as a misled reader.** Who reads it (API caller, operator, next maintainer), what they do because of it, what happens: "Caller follows the docstring and passes `timeout=30` meaning seconds; `client.py:52` now treats it as ms, so requests time out after 30 ms." If the worst you can write is "the reader is briefly puzzled", it is below the bar.
8. **Separate doubt from ambiguity.** Both quotes, a verified prior state and the other layers checked justify 85 or more. If one of those could not be checked (no base version, a wrapper you could not locate), say which in `evidence` and lower `self_confidence`. Ambiguity is different: if the prose can reasonably be read in a way that is still true, there is no contradiction to verify — drop it.

## False positives specific to this lens
- **History by design.** Old changelog entries, migration guides ("before 2.0 …"), ADRs, versioned docs (`docs/v1/`), deprecation sections and blog posts describe the past on purpose. Check the heading or version the passage sits under.
- **Generated docs.** typedoc/Sphinx/rustdoc output, cobra- or clap-generated markdown, OpenAPI emitted from annotations, README regions between generated markers, `--help` snapshots. Look for a "generated / do not edit" header, a generator script or a CI freshness check; the source of truth is elsewhere.
- **Examples CI already executes.** Rust doc tests, Go `Example…` functions, Python doctests wired into pytest, type-checked markdown snippets. Read the CI config; if they run, a broken example fails the build without your help.
- **Illustrative snippets.** Pseudo-code, `...` elisions, placeholder values, curl against an example host. Judge only the names, arguments and flags this change touched, not whether the snippet is complete.
- **Same word, different thing.** A search hit for `timeout` or `--output` in the README may belong to another command or component. Confirm through the section heading, import path or command name.
- **Approximations and intent comments.** "About 5 minutes" for 270 s, "usually", "roughly", and comments that explain why rather than what. Not false, so not a finding.
- **Commented-out code.** It is disabled code, not a claim about behaviour; whether it should exist is not this lens's question.
- **Declared follow-up.** The description or brief says the docs land separately ("docs PR to follow", a linked ticket). The human reviewer already knows; put one line in `notes`. A red-case contradiction is still reported, because users can be hurt before the follow-up lands.
- **Missing docs.** A new parameter, flag or function without documentation is outside this lens — unless existing text became false because of it ("takes no options", "always returns a list").
- **Wording, grammar, typos, formatting, comments that restate code.** The one exception: a typo inside a command, flag, identifier, path or URL that makes copy-paste fail is a broken example.

## Severity guide
Almost everything here is `yellow`: a comment or doc that now lies, with a bounded cost to whoever trusts it.

`red` is reserved for text that leads someone who follows it faithfully to destroy data or expose secrets or private data — and you have confirmed the code path:
- `prune --help` says "asks for confirmation"; this change removed the prompt, so the documented command deletes immediately.
- An upgrade guide added here says "roll back with `migrate down`, no data loss"; the down step drops a column the up step populates.
- README says tokens are "masked in debug output"; this change added a debug log of the full request headers.

`yellow` examples:
- Docstring says "returns `null` when missing"; the function now throws `NotFoundError`.
- README documents `--output-dir`; the change renamed it to `--out` with no alias, so the documented command fails with "unknown option".
- `// retry up to 3 times` above `MAX_RETRIES = 5` edited here; `.env.example` still lists `DB_URL` after the code switched to `DATABASE_URL`.

Below the bar, besides everything in the false-positive list: comments that narrate the change ("now uses X"); stale TODOs that would mislead no one; dates, authors, licence headers; text that is imprecise but not false.

An example that recommends `verify_ssl: false` or contains a real-looking credential is not an accuracy problem, because no code contradicts it. If you happen to see one, report it once under `category: "security"` as the contract allows; do not go looking for more.

## Cheapest proof
`test_idea` is for the verifier; you do not run project commands yourself. The verifier may not be allowed to execute code either (fork PRs), so lead with a proof that works by reading or searching and offer a runnable one second. Name one command and the output that proves the text wrong:
- **Search:** `git grep -n "output-dir" -- "*.md" docs/` hits README.md:41 while `git grep -n "output-dir" -- src/` returns nothing — the documented flag is undefined.
- **Causation:** `git show <base>:src/client.py | grep -n timeout` shows the text was true before this change (`<base>` as in Confirm step 4).
- **Run the documented command:** `mytool export --output-dir out` prints "unknown option"; or diff `mytool --help` against the README usage block.
- **Paste and run the example:** `python -c "from pkg import fetch; fetch(u, retries=3)"` raises `TypeError: unexpected keyword`; also `npx tsc --noEmit snippet.ts`, `python -m doctest path.py`, `cargo test --doc`, `go vet ./examples/...`.
- **Assert the documented behaviour:** a three-line unit test, `assert find("missing") is None`, which currently raises `NotFoundError`.
- **Print the real value:** `python -c "import cfg; print(cfg.DEFAULT_TIMEOUT)"` against the documented "30".

For a pure comment-versus-code contradiction nothing needs to run: write "read-only: compare <path:line> with <path:line>" so the verifier does not spend an execution on it.
