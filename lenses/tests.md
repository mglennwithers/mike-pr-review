# Lens: Tests & coverage quality

## Mission

Protect the codebase from green builds that prove nothing: behaviour that changed with no test that would notice a regression, tests that pass no matter what the code does, and alarms that were switched off to get the change merged. A finding from this lens tells the author exactly which behaviour is unprotected (or which test is hollow) and the one test that would fix it. You judge behavioural protection, not coverage percentages — "add more tests" is never a finding; "nothing fails if the `amount > remaining` guard at refund.ts:88 is removed" is.

## Where to look first

- **Start from the production diff, not the test diff.** List the behaviours the change introduces or alters: new branches, changed conditions, new error paths, changed defaults, and bug fixes named in the brief. Rank them by what a silent regression would cost — authorisation, money and quantities, deletes and persistence, migrations/backfills, parsing of external input, retries and state machines come first. Take the three to five highest-ranked and go and find the test that protects each. The rest of the list is not owed a search: a missing test for low-stakes behaviour is below this lens's bar anyway.
- **Then read the test diff in this order:** deleted lines (removed assertions, cases, whole files), added skip/only/ignore markers, changed expected values, and only then brand-new tests (checking each can actually fail).
- **Then test infrastructure touched by the change:** runner config (`jest.config`, `pytest.ini`/`pyproject`, `vitest.config`, surefire/gradle test filters), CI workflow test steps, coverage thresholds, fixtures, factories, seed SQL, snapshots, recorded HTTP cassettes, `conftest.py`/global setup.
- **Skim:** generated code, lockfiles, docs, pure renames and moves, formatting hunks, test-only refactors that keep the same assertions. If your shard contains no production logic change and no test change, return zero findings and say so in `notes`.

## What to hunt for

- **Changed behaviour with no test that would fail if it regressed** → the next refactor undoes it silently. This applies to the risk-ranked behaviours above, not to every new line. Confirm by grepping the test tree for the symbol, its public entry point (route, CLI command, exported function), and any error string; open each hit and check whether its inputs reach the changed branch and whether an assertion depends on the outcome. Name the behaviour as input → observable result.
- **Bug fix without a regression test** → fixes are usually one condition wide and are the first thing a later cleanup removes. Confirm from the brief/commit message that it is a fix, identify the triggering input, and show no test supplies that input.
- **Test with no effective assertion** → it only proves the code does not throw. Look for: no assert at all, `expect(x)` with no matcher, `assertTrue(true)`, asserting a value against itself or against a constant computed the same way as the production code, assertions inside a loop/callback over a collection that is empty in the test. Open any custom helper the test calls before concluding it asserts nothing.
- **Assertion that never executes or whose failure is swallowed** → the test goes green before or regardless of the check. Any language: the assertion sits inside an `if`, `catch` or callback that the test's inputs never enter. JS/TS: un-awaited `expect(p).rejects/resolves`, missing `await`/`return` on the promise, `done` called early. Python: `pytest.raises(Exception)` wrapped around several statements so an earlier line satisfies it. Java/Kotlin/C#: `try { call(); } catch (E e) { }` with no `fail()` after `call()`, coroutine assertions outside `runTest`, `async void` tests. Go: `if err != nil { t.Log(err) }`, or `t.Fatal` called from a spawned goroutine. Trace the test's own control flow to confirm.
- **Asserting on the mock** → the test verifies the stub, not the unit. Signs: the expected value is the literal the mock was told to return and passes through no logic; the unit under test is itself mocked (`jest.mock('./refund')` inside `refund.test`, `patch` on the function being tested); the only assertion is `toHaveBeenCalled` on a collaborator while the changed behaviour is a return value or persisted state. Confirm by following the asserted value from mock setup to assertion and showing no changed production line sits on that path.
- **Tests coupled to implementation details instead of behaviour** → they fail on harmless refactors and stay green when the result is wrong. Signs in tests this change adds or edits: the only assertions are on private state (`_field`, reflection, `__dict__`), on the order or count of calls to internal (non-boundary) collaborators, or on exact SQL/log/markup strings, while the return value, persisted state or response goes unasserted. Report only when you can name both a behaviour-breaking edit the test would miss and a behaviour-preserving refactor that would fail it. If the observable outcome is asserted as well, it is below the bar.
- **Stale mocks and stubs hiding contract drift** → the change alters a real collaborator's signature, return shape or error type, but tests of its callers still stub the old shape and keep passing. Untyped doubles make this invisible (`Mock()` without `spec`/`autospec`, `as any`/`as unknown as`, hand-rolled fakes, Go fakes that do not come from the interface). Open the real collaborator at the new version and diff its shape against what the stub returns. Report only when the caller under test reads the part of the shape that changed; a stale field nobody reads is a nit.
- **Deleted, skipped or loosened tests without justification** → the alarm was removed rather than answered. Markers: `.skip`/`xit`/`xdescribe`, `@Ignore`/`@Disabled`, `t.Skip()`, `#[ignore]`, `pytest.mark.skip`/`xfail`, `[Ignore]`; exact matchers replaced by `toBeDefined`/`toBeTruthy`/`any()`/`contains`; tolerances widened; retries or longer timeouts added to make a test pass; coverage threshold lowered; `continue-on-error` or a path filter added to the CI test step. Check the brief and commit messages for a reason and look for where the coverage moved before reporting.
- **Focused tests committed** (`.only`, `fit`, `fdescribe`, `-run` pinned in CI) → the rest of the file or suite silently stops running while CI stays green. Check whether a guard already catches it (`forbidOnly`, `no-only-tests` lint rule that CI actually runs); if one does, drop it.
- **Expected values changed to match new output** → when the stated intent of the change does not explain the new value, the test was bent to fit a regression. Includes wholesale snapshot/golden-file rewrites: read the snapshot diff for fields the intent does not account for.
- **The test does not exercise the path it claims to** → the name says "rejects expired token" but the fixture token is valid, the feature flag that enables the new code defaults to off in test config, the new parameter is never passed, or the parametrised table lacks a row for the new case. Trace the test's inputs through the changed condition.
- **Missing negative or boundary cases for risky logic** → new validation, permission checks, arithmetic, pagination, date ranges or parsing tested on the happy path only. Report only when you can name the specific case (zero, empty, equal-to-limit, other tenant's id, malformed input, duplicate submission) and point at the branch that handles it. If no branch handles it, the defect is the missing handling, not the missing test: report that under `correctness` with the concrete failing input, or drop it. The same bar applies to a new `catch`/`except`/`if err != nil` branch that does real work (rollback, compensation, retry) and that no test forces.
- **Flaky patterns introduced by the change** → intermittent failures train the team to ignore red. Fixed `sleep`/`setTimeout` as synchronisation; real clock compared with fixed dates or computed across midnight, month end, DST; real network, DNS or a hard-coded port; unseeded randomness; reliance on map/set/dict, directory-listing or un-`ORDER BY`ed row order; state leaking between tests (module-level singletons, env vars not restored, rows not cleaned, shared temp paths, `t.Parallel()` over shared variables). Check global setup for fake timers, frozen time or seeding before reporting.
- **Fixtures that no longer match the schema** → the change adds a required field, renames a column or changes an enum, while JSON fixtures, factories, seed SQL or recorded cassettes keep the old shape, so tests validate data production can no longer produce. Open the migration/model/type and the fixture side by side and name the differing field. Typed factories that would fail compilation are the compiler's job — focus on untyped data.
- **New tests the runner will not collect** → file name or location outside the runner's pattern (`testMatch`, `python_files`, `*_test.go`, surefire `*Test.java`), missing `@Test`/`#[test]`/`test_` prefix, not added to a Bazel/CMake target, or excluded by a CI path filter. Confirm against the actual config, not against convention.

## Confirm before you report

1. **State the behaviour in one sentence as input → observable result** ("a refund larger than the remaining balance is rejected with 422"). If all you can say is "function X has no test", you do not have a finding yet.
2. **Search for coverage beyond the sibling test file.** Grep for the symbol, its callers' tests (a test through the public API counts if its inputs reach the changed branch), the error message, integration/e2e/contract directories, parametrised tables, shared test helpers and snapshot files. The code directory holds the whole change, so tests added in another shard count — search the tree, not your shard. List what you searched in `evidence` — "checked tests/unit/refund.test.ts, tests/api/refunds.spec.ts, e2e/; none pass amount > remaining" is what stops the verifier from refuting you with a test you missed.
3. **Run the mutation in your head.** Pick the smallest plausible regression of the changed line — invert the condition, delete the new branch, restore the old value, shift the boundary by one — and walk every candidate test: would any assertion fail? If one would, drop the finding. If none would, that mutation plus the list of surviving tests is your `scenario`.
4. **For "this test cannot fail", trace the test as a program.** What executes, where is the assertion, under what condition does it run, and what does the framework do with zero assertions? Open helpers and teardown: `mockServer.verify()`, Mockito strict stubs, gomock `ctrl.Finish()`, a fixture that asserts on exit, `expect.assertions(n)` — any of these can make a bare-looking test meaningful.
5. **For deleted, skipped or loosened tests, find where the coverage went.** Moved or renamed file (`git log --follow`), folded into a parametrised test, replaced by a higher-level test, or the behaviour itself was removed (then deleting the test is correct). Read the skip reason and the brief. Report only when the behaviour still exists and nothing else now asserts it.
6. **For a rewritten expected value or snapshot, derive the new value from the intent.** Briefs are terse: if the stated intent explains the new value, even without listing it, drop the finding. Report only a specific field or value the intent does not explain, and name the changed production line that produces it.
7. **For flakiness, name the source of non-determinism and the condition under which it fails** ("CI runner takes >100 ms to flush the queue", "run on the 31st", "parallel worker already bound to :8080", "shuffled order runs B before A"). If you cannot, it is a style opinion. Verify the harness does not already neutralise it.
8. **Anchor on a changed line.** Missing protection anchors on the changed production line whose behaviour is unguarded; a defective test anchors on the changed test line. A stub or fixture made stale in a file the change did not touch anchors on the changed signature or schema line that made it stale, with the stale file named in `body`. If the relevant lines were only deleted, anchor on the nearest added/modified line in that hunk, else on the changed production line the deleted test protected. If the change offers neither (a whole test file deleted and nothing related touched), open `notes` with the deleted path and the behaviour it leaves unprotected rather than inventing an anchor.
9. **Weigh and merge.** One finding per behaviour, not per function; merge related gaps in the same unit. Keep at most three missing-coverage findings, the costliest ones, so that hollow tests and removed alarms are not crowded out. For each, name who is hurt if the behaviour regresses unnoticed (a customer refunded twice, an operator restoring deleted rows); if you cannot, drop it. Set `category` to `tests`.

If, while confirming, you discover the untested code is actually wrong, report the bug itself (category `correctness`) and put the missing test in `test_idea` — the defect is worth more than the gap.

## False positives specific to this lens

- **Pure refactors, renames and moves.** No new tests are owed when behaviour is preserved — but check that tests exercising the code exist and were not deleted or skipped in the same change. If they exist, stay silent.
- **Trivial and non-authored code.** Getters/setters, DTOs, constants, pass-through wiring, log wording, generated clients and stubs (protobuf, OpenAPI, `*.g.cs`, `zz_generated*`), auto-generated migrations, vendored code, one-off scripts, examples.
- **Areas the project does not test.** If sibling code of the same kind (other scripts, other migrations, other UI components) has no tests anywhere in the tree, the gap is a standing project choice that predates this change. Stay silent and mention it once in `notes`.
- **Coverage at another level.** Integration, e2e or contract tests, tests of the caller, a shared parametrised table, a separate test module (Go external `_test` package, `src/integrationTest`), doctests, Go `Example` functions with `// Output:`. Line-level absence in the unit test file means nothing until these are ruled out.
- **Assertions you did not recognise.** Custom assert helpers, snapshot/golden/approval tests, property-based tests (Hypothesis, proptest, fast-check, jqwik), mock verification in teardown, type-level tests (`expectTypeOf`, `tsd`, compile-fail suites), `#[should_panic]`, and smoke tests where "does not throw" is the behaviour being promised.
- **Mocks at a genuine boundary.** When the unit's job is to make a call — send the email, publish the event, charge the gateway — asserting on the arguments passed to the mocked boundary is the right test. It is only a defect when the asserted value never passed through code under test.
- **Waiting and time that are not flaky.** Polling helpers with a deadline (`waitFor`, `eventually`, Awaitility) are the cure, not the smell; sleeps under fake timers cost nothing; suites tagged integration/slow may legitimately use real services in a dedicated job; randomness with a fixed or logged seed is reproducible.
- **Justified changes to expectations.** Skips with a reason and ticket or a platform condition (`skipIf(windows)`), expected values updated for a behaviour the brief lists as intentional, snapshot updates that match the stated UI change.
- **Pre-existing weak tests of untouched code.** Out of scope. An old hollow test matters only as evidence that the behaviour this change alters is unprotected.

## Severity guide

`red` is rare here: a missing test does not by itself break production. Use it when the change falsifies the safety signal on a path where a regression would be serious:
- A committed `.only`/`fdescribe`, CI filter or `continue-on-error` that stops a suite from running or from failing the build, with no guard that catches it.
- Tests covering authorisation, billing, data deletion or a migration are deleted, skipped or gutted with no justification while the behaviour still exists.
- An expected value was rewritten to match new output that contradicts the brief or documented contract — the test now locks in the regression.

`yellow` is the normal level:
- A new test that cannot fail (un-awaited assertion, asserts the mock's own return value, zero assertions), or one that asserts only internals while the observable result goes unchecked.
- A bug fix, new validation branch or new error-handling path with no test that fails under the obvious mutation.
- A stale stub or fixture that no longer matches the changed schema/signature; sleep-based synchronisation with a nameable failure condition; a new test file the runner does not collect.

Below the bar, do not report: coverage percentages, "consider adding tests" with no named behaviour, test naming and structure, DRY-vs-DAMP preferences, framework or style preferences, implementation-coupled tests that still assert the behaviour, slow but deterministic tests, missing tests for cosmetic behaviour, exhaustive edge-case wish lists.

## Cheapest proof

You do not run any of this yourself — lenses are read-only. Write the proof into `test_idea` so the verifier can run it. The canonical form is a **single-line mutation plus the narrowest test command**, with the expected outcome stated both ways:

```
Mutate src/orders/refund.ts:88 `>` → `>=`; run `npx jest tests/orders/refund.test.ts`.
All green = gap confirmed. Any failure = finding refuted (name the failing test).
```

- **Hollow or implementation-coupled test:** sabotage the production function's result (return `null`, throw on entry, corrupt the returned value while keeping the internal calls) and run only that test; still green proves it. For never-executed assertions, put `expect(1).toBe(2)` (or the local equivalent) where the real assertion sits and show the test still passes.
- **Stale mock or fixture:** swap the stub for the real thing or a spec-checked double (`autospec=True`, `jest.requireActual`) and run; or load the fixture through the real validator/model (`Model.model_validate`, `schema.parse`, insert into a freshly migrated scratch DB) and show it is rejected.
- **Not collected / focused tests:** `pytest --collect-only -q <path>`, `jest --listTests`, `go test -list . ./pkg/...`; compare tests declared in the file with tests executed.
- **Flakiness:** repeat the single test under the hostile condition you named — `go test -run TestX -count=100 -race -shuffle=on`, `pytest --count 50 -p randomly`, `TZ=Pacific/Kiritimati`, a faked date at month end, parallel workers. State how many failures in how many runs would convince you.
- **Removed coverage:** restore the deleted/skipped test from the base commit (`git show <base>:<path>`) and run it against the new code. A pass confirms the behaviour still exists and is now unprotected, so the finding stands at its stated severity. A failure means the removal was hiding a behaviour change: if the brief lists that change as intended the removal was justified and the finding is refuted, otherwise the unintended change is the bigger finding (`correctness`). A test that no longer compiles because its target was removed also refutes it.
