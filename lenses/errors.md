# Lens: Error handling & silent failures

## Mission

Protect the codebase from failures that nobody finds out about: an operation breaks, the code carries on, and the caller, the user or the on-call engineer is told everything went fine. These bugs pass every happy-path test and surface weeks later as missing data, double charges or an undiagnosable incident. "Add error handling here" is the cheapest review comment to produce and the first one authors learn to ignore, so a finding from this lens (`category: "errors"`) has to say which failure is hidden, who is misled by it, and what wrong state results.

## Where to look first

- Learn the repo's safety nets once, before judging any hunk — most false positives in this lens come from not knowing them. Find the error middleware or exception filter, the global unhandled-rejection/uncaught-exception hook (does it crash, or log and continue?), any transaction wrapper or decorator around handlers and jobs, and whether CI enforces `errcheck`, `no-floating-promises`, `#[must_use]` or unused-result warnings.
- Rank changed hunks by what they touch. Highest: I/O and side effects (DB writes, HTTP/RPC calls, queues, payments, file writes, subprocesses), then anything that adds or edits `try/catch/except/rescue/recover`, `finally/defer/with/using`, `.catch`, `Result`/`Option` combinators, `if err != nil`, retry loops, or default operators (`||`, `??`, Kotlin `?:`, `.get(k, default)`, `unwrap_or*`, `getOrElse`, `COALESCE`).
- Look at what the change *removed*: a deleted `throw`/`raise`/`return err`, a dropped `await`, a `check=True` or `raise_for_status()` that disappeared, a transaction wrapper that no longer encloses a call. Anchor on the changed line that replaced it; if the hunk only deletes, use the line now sitting where the removed one was and quote the removed line in `evidence`.
- Look at what the change *added inside an existing handler*: a new failable call placed in an old `try` whose catch swallows is a new silent failure even though the catch line is unchanged. Anchor on the new call.
- Boundaries decide the outcome: HTTP handlers, job/cron entry points, message consumers, CLI `main`, shell/CI scripts. Read how they turn an error into a status code, ack, exit code or UI message.
- Skim: pure computation, type/DTO definitions, tests and fixtures, generated code, docs.

## What to hunt for

- **Swallowed failure** — empty `catch {}`, `except: pass`, `contextlib.suppress`, `.catch(() => {})`, Ruby `rescue nil`, Go `_ = f()` / `_, _ :=`, Rust `let _ = res;` / `.ok();`, and `return`/`break`/`continue` inside a `finally`, which discards the exception in flight. The code after it runs as if the step succeeded. Confirm by reading what the following lines and the caller assume happened (a saved row, a sent message, an initialised value).
- **Catch-all around a narrow intent** — `except Exception`, `catch (Throwable)`, bare JS `catch (e)` wrapping a large body to handle one expected case (not found, parse error), so every other failure gets the same treatment. Confirm by opening the callees and naming a *second* failure that realistically occurs in the body — timeout, permission denied, 5xx, malformed payload, or a key/attribute error on data the change itself shows can be absent — and show the handler's response is wrong for it (a timeout read as "user not found" creates a duplicate). "A future bug would be hidden" on its own is not a scenario.
- **Cancellation and interrupts eaten** — bare `except:` / `except BaseException` catching `KeyboardInterrupt`, `SystemExit` or `asyncio.CancelledError` without re-raising (`except Exception` does not catch these on Python 3.8+); Java `InterruptedException` caught without `Thread.currentThread().interrupt()`; Kotlin `catch (e: Exception)` inside a coroutine eating `CancellationException`; Go retrying on `context.Canceled`/`DeadlineExceeded`. Timeouts stop working and shutdown hangs. Confirm something actually cancels or interrupts this code (a timeout wrapper, `wait_for`, a shutdown hook, a request context) and that the handler neither re-raises nor restores the flag.
- **Fallback value that masks failure** — `fetch().catch(() => [])`, `(await load()) ?? 0`, `unwrap_or_default()`, `getOrDefault`, returning `null`/`false`/`{}` from a catch. This is a finding only when the defaulted expression is the result of an operation that can fail, so the caller cannot tell "no data" from "lookup failed". Open every caller and see what it does with the default: renders an empty state, caches it, or — worst — feeds it into a write, delete or authorization decision.
- **Logged but not propagated** — catch, log, return normally. Harmless for side tasks; a bug when the caller reports success on the back of it. Trace up to the boundary: does the handler return 2xx, the job get marked complete, the consumer ack, the offset commit, the UI show a success toast?
- **Lost cause or error identity** — Python `raise X(...)` outside the `except` block or with `from None`; JS `throw new Error(msg)` without `{ cause }`; Java `new X(e.getMessage())`; Go `fmt.Errorf("...: %v", err)` or `errors.New` replacing `err`; Rust `map_err(|_| ...)`. Report it in two cases only: a caller that branches on the error can no longer match (grep callers for `errors.Is/As`, `instanceof`, `except SpecificError`, `e.code ===`, retry classifiers, and cite the one that breaks), or the original error is neither attached nor logged anywhere on the path and the replacement message does not say which operation failed.
- **Handler or cleanup that replaces the original error** — a catch block that reads `e.response.data.message` when network errors have no `response`, so a `TypeError` surfaces instead of the real cause; a rollback, `close()` or `__exit__` in `catch`/`finally` that can itself throw and overwrite the first exception. Confirm by opening the client library's error type or the callee to list the error shapes that reach the handler, and check the field exists for each.
- **Partial-failure state** — step 1 commits (row inserted, card charged, file written, event published), step 2 can fail, and nothing rolls back or compensates. Also batch loops that abort midway, and `Promise.all` that rejects while siblings keep mutating. Confirm there is no enclosing transaction (decorator, middleware, unit-of-work, `@Transactional`), that retrying the whole operation would not be idempotent, and that no reconcile job exists.
- **Missing cleanup on the error path** — an early `return`/`throw` added between acquire and release, with no `finally`/`defer`/`with`/`using`/try-with-resources. Locks, connections, file handles, temp files, open transactions, and UI "loading"/"in progress" flags that never reset. Walk every exit path in the new code between acquire and release; in Go also check `defer` inside a loop and `defer` registered after the early return.
- **Retries that make things worse** — a loop with no attempt limit, retrying every error including validation/4xx, retrying non-idempotent operations (charge, send email, `INSERT` without an idempotency key), a tight loop with no delay against a shared dependency, or falling out of the loop after the last attempt as if it succeeded. Open the retry helper or library config for its real defaults, and the callee for idempotency support.
- **Unchecked result** — Go `err` ignored, shadowed by `:=` in an inner scope so the outer `err` stays nil, or handled with `if err != nil { return nil }`; checking the wrong variable; C return codes; `fetch` without `res.ok` (it does not reject on 4xx/5xx); `requests` without `raise_for_status()`; `subprocess.run` without `check=True`; ignored affected-row count on an `UPDATE ... WHERE version = ?`; `rows.Err()`, and `Close()` errors on *written* files. Confirm how the callee signals failure by opening it or its docs in the repo.
- **Async failures that go nowhere** — `return promise` inside `try` (the catch never fires; needs `return await`), floating promises, `forEach(async ...)`, a missing `'error'` listener on a stream/emitter (crashes Node), `asyncio.create_task` whose result is never awaited, `gather(return_exceptions=True)` whose results are never inspected, `executor.submit` futures never read, Kotlin `launch` without a handler. State what the global hook you found earlier does with the stray failure — a crash and a quiet log line are different findings.
- **Null-safe operator skipping a required step** — `user?.save()`, `onCommit?.()`, `if let Some(x) = ...` with no `else`, `obj&.persist`. The operation silently does not happen. Report only when you can name the realistic state in which the receiver is absent (check the types, schema and callers) and cite the downstream line that assumes the step ran.
- **Wrong signal at the boundary** — handler catches and returns 200 / `{ success: true }`; script without `set -e`/`pipefail`, or `|| true` / `continue-on-error` on a step that matters; consumer acks a message it failed to process (lost) or nacks a poison message forever (redelivery storm). Read the framework's ack and exit-code semantics in config before claiming either.
- **Fallback to a stub or default config in production code** — config parse failure falls back to defaults, a missing env var becomes `localhost` or a test key, a failed client init is replaced by a no-op implementation. Confirm which environments execute this path and whether anything announces the degradation (startup log at error level, health check, metric).
- **User-facing error text** — responses that include `str(e)`, stack traces, SQL or file paths; or code that has a specific, user-fixable reason in hand (validation detail, 409 conflict, quota exceeded) and collapses it into "Something went wrong". Check whether error middleware sanitises output and whether the leak is gated by a debug flag. If a secret or credential can leak, report it with `category: "security"`.

## Confirm before you report

The verifier will repeat these steps trying to refute you, so a finding that skips one is a finding you will lose. If a step cannot be completed from code you have read, read more or drop it.

1. **Name the failure.** Identify the specific call that can fail and how — timeout, constraint violation, 404, malformed input — or, for null-safe and default cases, the state in which the value is absent. Open the callee to verify it really can raise or return that on a realistic path. If it cannot fail, or only fails when the process is already dying (out of memory, disk gone), drop it.
2. **Follow the failure to its observer.** Walk up the call chain from the handler to the boundary and state what the observer sees: status 201, job marked done, empty list, exit code 0. If anything on the way surfaces the failure — a wrapper rethrows, the middleware you found earlier converts it, the returned `Result`/error tuple is checked later — drop it.
3. **For defaults, prove indistinguishability and harm.** Show that the caller cannot tell the fallback from a legitimate value, and cite the line where it acts on it in a way that is wrong (persists it, deletes based on it, displays a false "none found").
4. **Rule out intent.** Look for a comment, a name (`tryX`, `bestEffort`, `xOrDefault`), the review brief, or sibling code that handles the same operation the same way on purpose. Best-effort is legitimate when the primary result does not depend on the step.
5. **Show what the change did.** Use the diff and `git show`/`git blame` to separate new behaviour from moved or re-indented code. In this lens "new" includes: a try body widened over a failable call, a failable call added under an old swallow, a rethrow removed, or a new caller that depends on a result an old handler swallows — anchor on that changed line, not on the old handler.
6. **Write `scenario` as fault → path → observed outcome**, e.g. "`repo.save()` rejects on unique-constraint violation → caught at orders.ts:52, logged → handler returns 201 at L60 → client believes the order exists." All three parts come from code you read, not from what usually happens in codebases like this.
7. **Give `evidence` both ends**: the line where the failure originates, the line that hides it, the line where the observer is misled, and which safety nets you ruled out (global handler, transaction wrapper, other callers). A `self_confidence` of 80 or more means you opened both the failing callee and the observing caller.
8. **One finding per root cause.** When the same pattern repeats across several new handlers, report the most harmful instance and list the other locations in `body` — five copies of one comment crowd out different defects.

## False positives specific to this lens

- **Ordinary defaults** — `opts.limit ?? 50`, `params.get("page", 1)`, `env.LOG_LEVEL || "info"`, an optional field rendered as empty. A default on optional *input* hides nothing; only a default on the result of a failable operation does.
- **Best-effort side work** — telemetry, metrics, cache reads/writes, optional enrichment, cleanup during shutdown, feature detection. Ask whether the function's primary result depends on the step; if not, swallowing is a design choice.
- **Catch-alls at a real boundary** — request handlers, worker loops, `main`, thread run loops, error middleware that log and return 500, rethrow, dead-letter or exit non-zero. A per-item catch that keeps a worker loop alive is correct as long as the failure is recorded somewhere an operator will see.
- **Errors translated, not swallowed** — a catch that returns `{ ok: false }`, an `Either`, an error tuple or a sentinel the callers do check. Follow the return value before calling it swallowed.
- **The framework already handles it** — async route handlers in frameworks that forward rejections, `@ControllerAdvice`/exception filters, `@Transactional` rollback, React error boundaries, test runners failing on unhandled rejections. Check the version and config actually in the repo.
- **The linter already handles it** — if CI enforces `errcheck`, `no-floating-promises`, `#[must_use]` or unused-result warnings, ignored returns and floating promises of that kind are CI's to catch. An explicit opt-out (`void sendMetrics()`, `_ = f() // best effort`) is a stated decision; question it only when step 2 shows real harm.
- **Deliberate fire-and-forget** — a background task with its own `.catch`/done-callback that logs, a task stored in a tracked set, a goroutine with `recover` and an error channel. The failure has an observer; it is just not the caller.
- **Narrow catches for an expected condition** — `except FileNotFoundError: return None`, `ENOENT`, `NoSuchElementException`. This is the pattern you want; do not flag it as "returns null on error".
- **Cause is preserved implicitly** — Python chains `__context__` automatically when raising inside an `except` block; Java/Kotlin constructors taking `e` as the cause argument; loggers given the exception object; an error logged in full just before a sanitised one is thrown to the client.
- **Results that cannot meaningfully fail** — Go `Close()` on read-only files, writes to `bytes.Buffer`/`strings.Builder`/`hash.Hash`, `fmt.Fprintf(os.Stderr, ...)`. Report ignored `Close`/`Flush`/`Sync` only on write paths, where it loses the write error.
- **Library retries with sane defaults** — SDK clients and resilience libraries are usually bounded with backoff out of the box. Open the config before claiming "unbounded"; the real question is whether the retried operation is idempotent.
- **Test, fixture, example and dev-tooling code** — a swallowed error there misleads no production observer. A test that cannot fail because of it belongs to the `tests` lens.

## Severity guide

`red` — the failure is hidden *and* the observer is told success while state is wrong, lost or duplicated, on a path that realistically occurs:
- `catch` around `db.save()` logs and the handler still returns 201; or a consumer acks a message whose processing threw.
- `remoteIds = await fetchIds().catch(() => [])` feeding a sync step that deletes every local record not in `remoteIds`.
- Card charged, then the order insert fails with no refund or compensation; a payment POST retried without an idempotency key.
- A newly floating promise or unhandled `'error'` event that crashes the process under an ordinary network failure.

`yellow` — a real defect that fails safely or mainly hurts diagnosis and UX:
- `%v` instead of `%w` disabling an upstream `errors.Is` used for retry classification; a cause dropped with nothing logged, so the surviving message cannot identify the failing operation.
- A catch block that throws `TypeError` on network errors and buries the real cause; `CancelledError` swallowed so graceful shutdown hangs until the process is killed.
- Temp file, handle or lock leaked on a rare error path; "loading" state stuck after a failed request.
- Stack trace or SQL text returned to clients (no secrets involved); a user-fixable validation reason discarded in favour of a generic message.

Below the bar: missing log fields or log-level preferences, message wording, "wrap this in try/catch" without a named failure, a missing `{ cause }` when the original is logged alongside, missing jitter or backoff on a bounded retry of an idempotent read, exceptions-versus-Result style debates, and an empty catch around something that cannot fail.

## Cheapest proof

You do not run any of this yourself; the verifier does, and your job is to make its run cheap. A good `test_idea` names the symbol to stub, the failure to inject, and the assertion on what the *observer* sees that currently passes but should not — and points at an existing test file whose harness can be copied.

- JS/TS: `jest.spyOn(repo, 'save').mockRejectedValue(new Error('db down'))`, then POST `/orders` and expect 500; currently 201.
- Python: `monkeypatch.setattr(client, "fetch_ids", Mock(side_effect=TimeoutError))`, then assert `sync()` raises and `repo.delete` was not called.
- Go: a fake implementing the interface that returns `errors.New("boom")`; assert the returned `err` is non-nil, or that `errors.Is(err, ErrNotFound)` still holds after the new wrapping.
- Error replaced in the handler: reject with an error that has no `.response`, then assert the original message reaches the caller rather than a `TypeError`.
- Partial failure: make step 2 throw, then assert step 1's effect is gone (row count unchanged, no event published).
- Cleanup: make the call after acquire throw, then assert the lock is released, the temp file is absent, or the connection is back in the pool.
- Async: a five-line script run with `node --unhandled-rejections=strict`, or a test asserting the returned promise rejects rather than resolving `undefined`.
- Shell/CI: run the script with the failing command forced (`PATH` shim or bad argument) and check `$?` is non-zero.

When no harness exists, offer a static proof instead: the grep showing that no caller checks the returned error or default, or the file:line list of distinct failures the try body can raise next to the single handler that treats them as one.
