# Lens: Performance & resource use

## Mission

Protect the codebase from changes that work on the author's laptop and fall over under production data or traffic: work that scales with the wrong variable, resources that are taken and never returned, and blocking calls on paths that must stay responsive. A finding from this lens is worth something only when it carries two arguments, each backed by a file:line you read: the code is on a path that runs often (or holds a scarce resource), and the data or traffic is large enough for the cost to be felt. A finding that says "this is slow" without both is speculation; one that says "this list endpoint now issues 1 + N queries and N is the customer's order count" saves an incident. Use `category: "performance"`.

## Where to look first

- Rank the changed code by reachability from an entry point that runs repeatedly: request handlers, queue/stream consumers, scheduled jobs over whole tables, render functions, per-row or per-message callbacks. Spend most of your time where that code touches a database, the network, the filesystem, or iterates a collection.
- A hunk often shows one innocent line (`const owner = await getUser(o.ownerId)`). Open the full file: the enclosing loop, `map`, comprehension, resolver or render is usually outside the hunk.
- Check both directions. The change adds a loop around an existing helper: open the helper and see whether it does I/O. The change adds I/O to an existing helper: search its callers for loop call sites. In the second case the victim is outside the diff; anchor on the added I/O line and name the looping caller in the body.
- Look closely at: new or modified queries, ORM calls and repository methods; model/schema files (to check indexes); anything added at module, static or singleton scope (maps, arrays, caches, clients); subscriptions and timers (`addEventListener`, `.on(`, `setInterval`, `subscribe`, `watch`); React components, hooks and context providers; regex literals applied to request input; serializers and response builders.
- Skim: tests, fixtures, docs, build config, type-only changes, renames, constants, one-off scripts. Neighbouring lenses own the adjacent ground: a migration's lock duration and rewrite cost belong to `data-migrations`; races, unbounded parallel fan-out and task/goroutine leaks to `concurrency`; retry storms to `errors`. Here you care how much work scales with data, whether a new query pattern has an index, and whether resources are released.
- Read the `-` lines too. A change that removes a cache, a memo, a batch call, a `LIMIT`, a clamp, an eager-load or an index is a performance change even though nothing "slow" was added. Anchor on the added or modified line that replaces what was removed; for a pure deletion, anchor on the nearest line in `changed_ranges` of that hunk and quote the removed line in `evidence`.

## What to hunt for

- **I/O inside a loop (N+1).** A query, HTTP call, RPC, cache get or file read per element: ORM lazy relations touched in a loop or serializer (`order.customer.name` in Django/Rails/Hibernate/EF), GraphQL field resolvers that fetch per parent, `for id in ids: repo.get(id)`. Each round trip costs milliseconds, so latency and database load grow linearly with the collection. Confirm by opening the query that produces the collection: is there `select_related`/`prefetch_related`/`includes`/`JOIN FETCH`/`Include()`/a DataLoader? Then check whether a batch form already exists in the repo (`WHERE id IN`, `getMany`, `mget`).
- **Unbounded result sets.** `findAll()`, `.all()`, `SELECT` without `LIMIT`, `list()` on an object store, an API that returns every row, or a `limit`/`pageSize` parameter taken from the request without a clamp. It works until the table grows, then the request times out or the process runs out of memory. Confirm by identifying the table or collection and how it grows, and whether a framework default (DRF pagination class, Spring `Pageable`, a gateway cap) already bounds it.
- **Loading rows to do what the database could do.** Fetching entities to count, sum, filter, sort, de-duplicate or check existence in application code (`len(qs)`, `.ToList().Count`, `findAll().filter(...)`), or pulling a blob or large text column for every row of a list that never uses it. Confirm the ORM call really materialises rows rather than compiling to SQL (`qs.count()` and `.Count()` on an `IQueryable` are SQL; `len(qs)` and `.ToList().Count` are not).
- **New query pattern without an index.** A `WHERE`, `ORDER BY`, `JOIN` or uniqueness lookup that this change adds, on columns no index covers. Open the schema, migrations or model annotations (`db_index`, `@Index`, `@@index`, `HasIndex`) and check composite indexes for a usable leftmost prefix. Postgres does not index foreign keys on its own while MySQL/InnoDB does, and a leading-wildcard `LIKE '%x'` or a function applied to the column defeats an ordinary index. Without a query in the diff that needs the index, there is no finding.
- **Accidental quadratic work.** `includes`/`indexOf`/`in list`/`find`/`contains` inside a loop over a collection of the same scale, nested loops joining two lists, repeated `list.remove`/`splice`/`insert(0)`, building a string or array by copying each iteration (`arr = [...arr, x]`, `concat` in `reduce`, a `clone` or immutable append per step), sorting inside a loop. Confirm both collections scale with data rather than being a fixed handful, then name the fix (set/map lookup, group once).
- **Repeated expensive work on a hot path.** Compiling a regex, constructing an HTTP/DB/SDK client, parsing config or JSON, reading a file, building a large lookup table, or computing a loop-invariant value inside a per-request or per-item body. Client construction is the costly one: a new client per call discards connection pooling and TLS sessions (`new HttpClient()` per request in C#, `requests.get` without a session in a tight loop, `new PrismaClient()` per handler, `sql.Open` per call in Go). Confirm by finding how the rest of the repo shares that object.
- **Blocking calls where the runtime expects non-blocking code.** `fs.readFileSync`, `execSync`, `crypto.pbkdf2Sync`, or `JSON.parse`/`stringify`/deep-clone of a data-scaled payload in a Node handler; `requests`, `time.sleep`, sync DB drivers or file I/O inside `async def`; `.Result`/`.Wait()`/`GetAwaiter().GetResult()` in ASP.NET; `runBlocking` or blocking JDBC on a coroutine/reactive/Netty thread; `std::fs` or `std::thread::sleep` in a tokio task without `spawn_blocking`. One blocked event loop or a starved thread pool stalls every concurrent request, not just this one. Confirm the function is reached from the async runtime and not from a worker thread, CLI or startup code. For `.Result`, claim a deadlock only where a synchronization context exists (classic ASP.NET, UI threads); on ASP.NET Core the honest claim is pool starvation under load.
- **Unbounded growth.** A module-level `Map`/dict/list used as a cache or registry keyed by user input, ids, URLs or timestamps with no eviction; `functools.lru_cache(maxsize=None)` or memoize on high-cardinality arguments (or on methods, which pins `self`); a cache key that can never repeat (contains a timestamp, request id or fresh object reference), so it costs memory and never hits; an in-memory queue or channel with no capacity and a producer that can outrun the consumer; metrics labels built from unbounded values. Confirm the key space is unbounded and the container outlives the request.
- **Resources taken and not released, or held too long.** Listeners, subscriptions, intervals and observers added without a matching removal (React `useEffect` without cleanup, `on` in a function called repeatedly); files, sockets, cursors, DB connections, HTTP response bodies not closed on every path (Go `resp.Body`, `rows.Close()`, missing `defer`; Python without `with`; Java without try-with-resources; C# without `using`; a pool connection not returned when an exception is thrown between acquire and release). Also an outbound HTTP call or sleep inside an open DB transaction, which pins a pool connection for as long as the remote side takes. Trace the error path and the early returns, not just the happy path. Pool exhaustion presents as a hang, which is why this is worth the effort.
- **Chatty calls that could be one.** Per-item writes where a bulk insert/`executemany`/pipeline/batch endpoint exists, per-key cache gets instead of a multi-get, a polling loop with no delay or backoff, independent network awaits issued one after another (`await a(); await b(); await c()` with no data dependency). Confirm each call is a real network round trip, the calls are independent, and neither ordering, a transaction nor a rate limit requires the sequence.
- **Whole payload in memory.** Reading an upload, export, file or large response fully into a buffer or string (`readFile`, `.read()`, `response.text()`, `ReadAll`, `toByteArray`) where the size is controlled by a user or grows with data; building a full CSV/JSON export in memory; an endpoint that now returns whole entity graphs because a serializer includes a nested collection; serialising a data-scaled object per request just to log or clone it. Confirm there is no size limit upstream (body-size middleware, proxy cap, validation).
- **Regex backtracking on untrusted input.** Nested or overlapping quantifiers (`(a+)+`, `(\w+\s*)+$`, `(.*,)*`, alternations that match the same prefix) applied to input whose length the caller controls, in a backtracking engine: JS, Python `re`, Java, .NET, Ruby, PCRE. One request can pin a core for minutes. Go `regexp`, Rust `regex` and RE2 are linear-time, so drop the suspicion there.
- **React re-render storms and effect loops.** A `useEffect` whose dependency is an object, array or function recreated every render and whose body sets state or fetches (a loop that hammers the API); a context provider whose `value` is a fresh object literal above many consumers; new inline objects or callbacks passed to a `React.memo` child that renders a data-scaled list, chart or table; an unvirtualised list of data-scaled length; a `key` that changes every render (`Math.random()`, a fresh id) and remounts every row. For a loop, trace the full cycle in `evidence`: effect sets state, render recreates the dependency, effect runs again. For a storm, name what drives the renders (keystroke, scroll, timer, socket message) and what makes the subtree costly.

## Confirm before you report

1. **Name the hot path.** Trace callers from the changed line up to an entry point and cite it as file:line: route, consumer, job, component. If the only callers are startup, a CLI, a migration, an admin tool or tests, drop it. For a published library function with no in-repo caller, the documented use is the path; say so.
2. **Cite the scale.** Find something in the repo that shows n or traffic is large, and put its file:line in `evidence`: rows are created per user action or the relation is one-to-many from users (cite the insert or the model relation); sibling code paginates, batches or streams the same data; fixtures, benchmarks, comments, docs or config (`MAX_BATCH`, `pageSize`, partitioned tables) state volumes; or the size comes straight from the request with no clamp, so an attacker picks n. A table name that sounds big is not a citation. If you cannot cite any of these, you do not have a finding.
3. **Do the arithmetic.** State the cost as a function, then plug in the number you cited: "200 orders per page → 201 queries, about 2 ms each → 400 ms added", "50k rows × 50k `includes` = 2.5 billion comparisons". For leaks and growth, state what accumulates per call and what it exhausts ("one connection per failed request, pool of 10"). As a rough floor, drop anything that adds under about 50 ms or 10 round trips to a request, a few million simple in-memory operations, or a few MB, unless it holds a scarce resource or an attacker chooses n.
4. **Look for the mitigation you might have missed.** Eager loading or a DataLoader on the query; an ORM identity map or request-scoped cache; a memo or singleton one level up; a bounded LRU; an index created in another migration, by a unique constraint or a primary key; default pagination in framework settings; cleanup in a `finally`, `defer`, `using`, context manager, destructor or effect return. List what you checked in `evidence`; the verifier will look in the same places.
5. **Show the change caused it.** Compare with the old version (`git show`, the `-` lines). The change must add the call, move it inside the loop, widen the collection, remove the bound, or put an existing slow helper on a hotter path. A pre-existing N+1 that gains one more column is not yours to report.
6. **Name a proportionate fix in `body`:** the batch method that already exists, the eager-load option, the index definition, the cleanup call. If the only remedy you can think of is a redesign, suspect that you are reviewing the architecture rather than this change; re-run step 5, and if the finding still stands, say plainly that no local fix exists and leave `suggestion` empty.
7. **Write the `scenario` as something measurable**: entry point, data size, expected cost now versus expected cost after the fix. "Could be slow with many users" will be refuted; "GET /api/orders?limit=10000 is unclamped at orders.ts:41 and loads 10k rows plus 10k item queries" will not.
8. **One finding per root cause.** If the same pattern recurs (five serializers touching the same lazy relation), report the hottest occurrence and list the other locations in `body`, so the findings budget goes to distinct problems.

## False positives specific to this lens

- **Cold paths.** Startup, config loading, migrations, seed and build scripts, CLIs, dev-only tooling, admin screens used by three people, tests. Sync I/O and quadratic loops there are fine. A scheduled job is allowed to be slow; it becomes a finding only when it loads an activity-scaled table into memory at once or makes a round trip per row across the whole table.
- **Small bounded n.** Enum values, feature flags, the columns of a form, tenants in a single-tenant app, or a function that only ever receives one page or chunk (check the caller's slice size). This kills in-memory complexity arguments entirely. It weakens but does not kill network N+1: 25 sequential round trips on every page view is still visible latency, so do the arithmetic before dropping.
- **It only looks like a query per iteration.** The relation was prefetched upstream, the ORM queryset is lazy and not yet evaluated, the repository method reads from a request-scoped cache, or the "client" constructor returns a pooled singleton. Open the callee before you count queries.
- **Sequential awaits on purpose.** Ordering requirements, one transaction, a rate-limited API, backpressure, or a loop that stops at the first hit. Parallelising those would be a bug. Two or three fast sequential calls are also below the floor in step 3 even when independent.
- **Blocking is the model.** Sync code in WSGI Django/Flask, servlet-per-thread Java, Go (goroutines block cheaply), worker threads, or a function run through `run_in_executor`/`spawn_blocking`/`Dispatchers.IO`. The pattern is a defect only on an event loop or a small shared pool.
- **Micro-optimisations.** Allocation in a loop, string concatenation of a few parts, spread versus push on small arrays, `useMemo`/`useCallback` missing on a cheap computation or on a prop passed to a non-memoised child, a re-render of a cheap component, `SELECT *` on a narrow table, "this could be cached" with no repeated cost shown. The contract puts these below the bar; adding "on a hot path" does not lift them over it.
- **Bounded key space or short lifetime.** A module-level map keyed by an enum or by configured tenants, or a "cache" created inside the request and discarded with it, does not grow.
- **Index already there or irrelevant.** Covered by a composite prefix, a unique constraint, a primary key, or an ORM default (Django `ForeignKey`, Rails `t.references` and EF Core index foreign keys without being asked), or the table is a small lookup. For regex: a linear-time engine, an anchored pattern with no nested quantifier, or input that is length-limited or not user-controlled.
- **Development-only React behaviour.** StrictMode runs effects twice in development; that is not a loop. An effect whose dependencies are primitives or stable refs does not re-fire just because the component re-renders.

## Severity guide

`red` — the change can take down or visibly degrade a realistic production path, and steps 1-3 show how with cited numbers:
- An unclamped or unpaginated query on a table that grows with user activity, in a request handler (timeouts, out-of-memory).
- A blocking call or effect loop that stalls everyone: `execSync` in a Node request handler, sync-over-async starving the pool on a busy ASP.NET endpoint, a `useEffect` that refetches on every render.
- A per-request leak of a scarce resource (pool connection not released on the error path, listener added per request), or catastrophic regex backtracking reachable from request input on a server.

`yellow` — a real, measurable cost with limited blast radius:
- An N+1 bounded by a page size, or on a secondary endpoint or nightly job; independent network calls in sequence that add visible latency to a busy handler.
- A missing index for a new filter on a table you can show grows with activity but is scanned only by a low-traffic path; a client or regex rebuilt per call on a busy path.
- A leak on a rare path (listener not removed when a modal unmounts), an unbounded cache with slow-growing keys, a full in-memory export of an activity-scaled collection that only operators trigger, backtracking regex that only trusted operators or the user's own browser can feed.

Below the bar: anything without a cited scale argument, cold paths, micro-optimisations, costs that depend on growth you cannot evidence from the repo, quadratic work over collections you cannot show exceed a few hundred elements, and stylistic preferences about hooks or query builders.

## Cheapest proof

Write `test_idea` for the verifier to run; your own proof is the reading you cite in `evidence`. A good one measures a count or a growth rate, not wall-clock speed on one input, and states the expected number so the verifier knows what refutes you.

- **N+1 / chatty calls:** a query- or call-count assertion at two sizes. "Seed 3 then 30 orders, call the list handler under `assertNumQueries` / a SQLAlchemy `before_cursor_execute` counter / Hibernate statistics / Prisma query log / a mocked client's call count; expect a constant (2), currently 1 + N."
- **Quadratic or repeated work:** time the function at n = 1k, 10k, 100k; linear grows about 10× per step, quadratic about 100×. Give the function name and how to build the input.
- **Missing index / unbounded query:** the exact SQL plus `EXPLAIN` (expect `Seq Scan` or `type: ALL` on the named table), or a schema grep showing no index on the columns. For unclamped limits: the request that returns more rows than the intended maximum.
- **Blocking call:** start the handler with a slow input and show a second concurrent request or a 10 ms timer is delayed until it finishes (event-loop delay), or point at the sync call's signature in the library.
- **Leaks and growth:** run the operation N times, including the throwing path, then assert the observable returns to baseline: `emitter.listenerCount`, pool checked-out connections, open file descriptors, map size, mount/unmount cycles in a component test.
- **Regex:** the exact adversarial string and an expected time, e.g. `'a'.repeat(30) + '!'` against the pattern takes seconds and doubles with each added character.
- **React:** a render counter or Profiler in a component test: one state change should render the child once, currently renders k times or never settles.
