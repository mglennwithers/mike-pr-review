# Lens: Hygiene (maintainability, types, docs & comments, conventions)

## Mission

Protect the next reader from four kinds of rot a change can leave behind: code that does nothing or now exists twice, a type that says one thing while the runtime does another, prose the code now contradicts, and a written team rule quietly broken. Deeper review profiles still run these as four separate lenses; here they are one because their findings are nearly always `yellow`, and reading every changed line four times cost more than it returned. The merge saves reading, not coverage: no other lens will catch a README that still teaches a removed flag or a helper this change orphaned. There is no `hygiene` category; each finding carries the category of the group it came from (see "What to hunt for").

Every finding here is a pair: a line the change added or modified, and a counterpart that proves the problem — the existing helper, the search that returns only the definition, the sentence that is now false, the wrong value and the line that mishandles it, the rule quoted verbatim. Without the counterpart you have an opinion, and the verifier will refute it.

The main risk of this lens is noise. It sits directly on two contract exclusions (style and naming, hypothetical future problems), its findings almost never block a merge, and authors know it: a reviewer who posts one style opinion gets their next three real comments skimmed. So put one question to every candidate: would the author read it, say "good catch" and fix it in five minutes, or would they shrug and call it taste? Opinions are dropped without trace. A confirmed defect that simply matters little — one stale inline comment, a stray debug print — is a different thing: report it with an honestly low `self_importance` (the contract defines the field) rather than inflating it or hiding it. Most changes produce nothing from this lens, and zero findings with an honest `notes` line is the expected result, not a failure.

Be economical, because this lens exists so the change is not read four times. Read the change once with all four groups in mind, and open a surrounding file only to confirm a suspicion you can already state ("is `formatMoney` still called anywhere?"), not to browse. The contract's read-around rule still holds for confirming a candidate; what this lens does not do is read unchanged code in search of candidates. Report at most 6 findings (this lens's own cap, tighter than the contract's) and prefer zero findings to padded ones. In `notes`, say which groups applied and what you checked.

## Where to look first

- **If the task's Facts section lists project convention docs, read them before the diff** and keep the handful of rules that are about the code artefact and checkable by reading a diff, noting each rule's file:line, strength ("must / never" vs "prefer / generally") and scope (paths, layers, languages). `CLAUDE.md` and `AGENTS.md` are written for coding agents, so most of their content (commands to run, how to commit, when to ask) cannot be violated by a diff. A nested doc governs only its own folder and the nearer doc wins; follow an explicit pointer ("see `docs/STYLE.md`") one hop and no further. If Facts marks a doc as modified by this change, keep the old wording at hand with `git show <base>:<doc>` (`<base>` is the base commit given in Facts). If Facts lists no convention docs, the Conventions group does not apply: skip it, and do not infer conventions from how the code looks.
- **Then make one pass over the patches, listing the facts the change altered as you go**: signatures (parameters added, removed, renamed, reordered, retyped), return values and thrown errors, defaults, constants that carry a unit or limit, flags, env vars, config keys, routes, renamed or deleted files and symbols. That one list drives both the docs check and the types check. Put four questions to each hunk: is this new thing used, and does it already exist elsewhere? does its declared type still tell the truth? did a sentence near it, or about it, just become false? does it trip a rule on your list?
- **Creation and replacement points carry most maintainability findings**: new functions over ~15 lines, new files, exports, parameters, flags, config keys and env vars; and call sites where the change swapped a helper, flag or config key for something else, which may have been its last use. In typed code, also scan added lines for escape hatches (`any`, `as X`, `as unknown as`, postfix `!`, `@ts-ignore`, `# type: ignore`, `cast(`, Go `x.(T)` without `, ok`, Kotlin `!!`). A hit tells you where to look; it is not yet a finding.
- **A changed fact is the suspicion that licenses a look outside the patch**: the doc block above a changed signature, the comments 10-15 lines either side of the hunk in the full file (an unchanged comment made false appears on no diff line), and one search for the *old* name of anything renamed or removed across `*.md`, `docs/`, `examples/`, help strings, `.env.example`, sample configs and code comments that point at it (`see parseConfig()`, `{@link OldClass}`). That search is the highest-yield move in this lens. Search by name, not by number; searching for "30" drowns you.
- **Prefer a search to a read.** One whole-word search settles "is this used", one search for a distinctive literal, error string or magic number finds a twin, one search finds stale prose. Spend them on the two or three largest new pieces of logic rather than on every hunk, and ask for several in one message.
- **Check for moves before judging a large added block** (`git show -M --stat`, or look for its first line among the diff's deleted lines). Moved code shows old warts as added lines, and they are not this change's.
- **Skim**: generated and vendored code (the one thing to look for there is a hand edit the docs forbid), lockfiles, snapshots, fixtures, old CHANGELOG entries, pure renames, one-line fixes. In tests look only for leftover debug scaffolding and for breaches of a written testing rule on your list ("no network in unit tests", "factories, not fixtures"); repetition and loose casts there are normal.

## What to hunt for

Four groups. Every finding's `category` must be exactly one of `maintainability`, `types`, `docs-comments`, `conventions` — the value beside the group it came from. Downstream code keys on these four strings, so do not write `hygiene`, a variant spelling or a compound. (The contract's off-lens rule is the only exception: a defect that is really a security or correctness bug takes that lens's category.) The items below are the ones that have mattered in practice. The shape alone is never the finding; the confirmed counterpart is.

**Maintainability** — `category: "maintainability"`
- **Dead code the change added or orphaned** — a new function, export, constant, file or branch that nothing reaches, or an existing helper, flag or config key whose last use this change replaced while leaving the definition behind. It gets maintained, misleads readers about what the system does, and often signals an unfinished wiring job. Confirm: search the symbol repo-wide, including string forms, re-exports, DI/route/plugin registration and templates. For an orphan, anchor on the changed line that replaced the last use; if the use was simply deleted and no changed line remains, leave it.
- **Logic duplicated next to an existing helper** — the change re-derives a business rule (pricing, permission check, validation, parsing) that already lives elsewhere, adds two copies of one itself, or hand-rolls retry, chunking, slugify or path building that the repo, the stdlib or an existing dependency already provides. The next fix lands in one copy and the other keeps the old behaviour. Reportable only when the copy is substantial (roughly 10+ lines of real logic) and must change whenever its twin does; strongest when the two already disagree on some input. Confirm: open the twin, compare line by line, walk the edges (empty, null, zero, non-ASCII, sync vs async, mutate vs copy) through both, cite both locations. Do not recommend adding a dependency.
- **Parameter, flag or option that does nothing** — accepted but never read, read with no effect on any output, or a config key or env var added to the schema and never consumed, so callers believe they are controlling something. Confirm: read the whole body and everything the value is forwarded to, and check that no interface, override or callback signature forces the parameter.
- **Name that promises what the body does not do** — on a function the change added or whose body it altered: `getUser` that inserts, `isValid` that mutates or throws, `sortedItems` never sorted, `disableCache=true` enabling the cache. Callers code against the name, so the mismatch becomes a bug at the call site. Confirm: quote a caller, ideally one in this change, that relies on the promised meaning. With no such caller, report only a read-sounding name (`get`, `is`, `has`, `find`, `validate`) on a body that writes, sends or mutates its argument, or an ordering or polarity the body contradicts. A name is reportable only when the behaviour contradicts it, never because a better name exists; a unit or nullability the name states belongs to Types below.
- **Debug leftovers and copy-paste residue** — `console.log`, bare `print`, `debugger`, `breakpoint()`, an `if (true)` short-circuit, a hard-coded localhost URL or sleep; a pasted block still carrying the source's error message, metric key or identifier. Confirm: check how the rest of the file logs and whether stdout is the program's real output; for residue, show the stale token next to the correct one in the source block.

**Types** — `category: "types"`. Escape hatches exist only in typed code, but a parameter list, a unit and a status value are contracts in any language, so the first and third items apply to untyped code too. Never ask for annotations that are not there, and a type that merely could be tighter is taste. The finding is a specific wrong value the new code can now build or accept, and the line where it does damage.
- **A type that now lies** — the change alters what a value is (unit, nullability, shape, meaning) while the declared type, annotation or parameter list still says the old thing: a return annotated `User` with a new `return None` path, `timeoutMs` now fed seconds, reordered parameters of the same primitive type, a field made nullable while readers still dereference it in a language or config that does not force them to update (Python, Go pointers, Java, non-strict TS). Confirm all three legs: the exact wrong value, a producer in or reachable from this change, and the victim line that misbehaves with it. When the change altered a meaning, the victims are the call sites it did not touch, so open those and compare order and units at each.
- **Escape hatch added on a risky path** — `as Foo` on parsed JSON or an HTTP response, `any` flowing into money, auth or persistence code, a bare ignore comment hiding a real mismatch, an unchecked Go assertion. The declared type becomes a lie and the failure surfaces far from its cause. Confirm: trace the value to its source, show the source can really produce another shape (optional in the provider's schema, nullable column, another variant), and that nothing validates in between. One exception to "no counterpart, no finding": an unvalidated external boundary feeding money, auth or persistence whose provider schema you could not reach — report it, say which leg is unproven, and keep `self_confidence` below 60.
- **New variant or status nobody handles** — a value added here that falls into a `default`/`else`/silent no-op in an existing switch or comparison chain the checker does not force to be exhaustive. Confirm: search every comparison on the old values and show what the fallback branch does with the new one.

**Docs & comments** — `category: "docs-comments"`. This group does not ask for more documentation and does not comment on wording. Each finding is a sentence someone will read, and the code that makes it false.
- **Doc block out of step with changed code** — a documented parameter that no longer exists or kept its old name, "returns null if not found" on a function that now throws, a new function whose docstring was pasted from a sibling. Callers code against the hover text, not the body. Confirm: compare the new signature and every `return`/`throw`/`raise` against the block name by name, plus any wrapper or decorator that could still supply the documented behaviour.
- **Unchanged comment or number made false by the code beneath it** — `// retry up to 3 times` above `MAX_RETRIES = 5`, "timeout in seconds" beside a value now treated as milliseconds, `// skip inactive users` above a filter that now also skips trial users. These live longest because no diff line highlights them, and a unit slip becomes a 1000x error in caller code. Confirm: read the whole function and how the constant is consumed (`sleep(t)` vs `sleep(t / 1000)`).
- **User-facing docs still teaching the old name or default** — README usage, `--help` strings, `.env.example`, sample configs, OpenAPI descriptions and pasteable examples that use a flag, env var, key, endpoint or signature this change renamed, removed or re-defaulted. An example that fails when pasted is the first thing a new user runs. Confirm: open the option's definition site (the parser or schema, not the handler) and look for a backwards-compatible alias before calling the old name dead.
- **Prose the change adds or edits that is false on arrival** — a CHANGELOG or migration-guide entry that says "now defaults to true" while the diff sets false, or "no breaking changes" while a documented flag is removed with no alias; a new comment, docstring or README sentence whose names, values, units, ordering or guarantees do not match the code. Confirm: pull each factual claim out of the added text and check it against the code at the new version (a changelog entry against the diff itself). Judge only the text this change adds or edits.

**Conventions** — `category: "conventions"`. Applies only when the task's Facts section lists convention docs; with none listed this group produces nothing, because a pattern you inferred from the codebase is not a rule. A finding here is worth exactly as much as its citation. Work rule by rule: for each rule you kept, search the added lines for its trigger (the banned import, the raw call the wrapper replaces, the file location, the missing companion).
- **Documented safety or data-handling rule broken** ("money is integer cents, never float", "never log request bodies", "every admin handler goes through `requireAdmin`") — check these first, because their breach is an incident rather than an inconsistency. Confirm: trace the added line to the value or sink the rule names, and check no wrapper one call up already applies the rule.
- **Hard rule broken by an added line** — a banned API or construct, an import across a written layer boundary, a mandated error/logging/i18n mechanism bypassed, a new file placed or named against a rule that test globs or migration runners key off, a required companion change missing (new env var absent from `.env.example`), a hand edit to a file the docs declare generated. Confirm: the sanctioned alternative exists and fits this call site; for an import, resolve where the target really lives (barrel files and path aliases hide it; a type-only import usually breaks nothing the rule protects); for placement, open the runner's glob; for companions, check the whole changed-file list in `context.json` and the repo, and anchor on the line that creates the obligation; for generated files, check the generator's input did not change in the same diff.
- **The rule or its enforcement edited to let the diff through** — "must" softened to "should", an exception path added, a lint rule switched off or a bare suppression added beside code that breaks the old wording. Rule changes deserve their own discussion, not a ride-along. Pair the doc or config hunk with the specific added lines that needed it, and judge the rest of the change against the old wording. Tightened or newly added rules are not findings, unless new code in the same diff already breaks them.

## Confirm before you report

1. **Produce the counterpart, with `path:line`.** Maintainability: the twin or helper, the caller the name misleads, or the exact searches you ran and what they returned. Types: the wrong value written out (`{status:'paid', paidAt:null}`, `transfer(orgId, userId)`), its producer and its victim. Docs: the doc sentence and the contradicting code quoted side by side, taken from the code directory rather than the patch (the fix may have landed in a file outside your shard), with the contradiction visible from the pair alone. Conventions: the rule copied verbatim from the doc, not paraphrased and not from memory. No counterpart, no finding.
2. **Prove this change caused it.** A verbatim move was not written here. A line that already broke the rule and was merely edited (`console.log(a)` became `console.log(a, b)`) is pre-existing. A comment that was already false, with neither it nor its fact touched, is pre-existing; you need "true before, false now", and the patch's removed lines or `git show <base>:<path>` show it. A cast on a moved line, or a loose type used the way its neighbours already use it, predates the change. Text, casts and rule-breaking lines the change itself adds are always in scope.
3. **Look for what would make it a non-issue, and cite where you looked.** Invisible users: reflection, decorators, DI containers, route tables, serializer field names, templates, public exports, interface or override requirements, tests. Guards: a type guard, schema parse or `isinstance` in the ten lines above a cast, validation middleware, DB constraints, a factory. Another layer keeping the doc true: a wrapper, decorator, base class, parser alias, deprecated-name shim, database default. Scope: a nearer convention doc that overrides the root one, a documented exception list, or a rule whose wording or purpose excludes tests, scripts or a CLI whose job is printing.
4. **Check whether tooling already says it.** Unused locals, imports and parameters, unreachable code, null and exhaustiveness holes where the build enforces them (Rust, Kotlin, Swift, strict TS/C#, strict mypy), doc examples that CI executes (doctests, Go `Example…`, Rust doc tests), and convention rules a lint or architecture check enforces are CI's to report. Open the lint or checker config and the CI workflow; if the rule is on and runs, drop the finding. What tooling cannot see — an unused export, a config key nobody reads, a stale README, a written rule with no linter behind it — stays yours.
5. **For a convention, check strength and that the rule is alive.** "Must / never / always": continue. "Prefer / generally": report only when the sanctioned alternative is importable from this file's layer, a sibling already uses it for the same job, and swapping it in needs no other change. Then run two searches in the same directory or package, banned form against sanctioned form; if the banned form is as common as the sanctioned one, the doc is stale — drop the finding and say so in `notes`.
6. **State the cost in the present tense.** `scenario` names who is misled today and what happens: "api/import.py:88 passes `strict=True` and gets no strictness because L40-71 never read it"; "caller follows the docstring and passes `timeout=30` meaning seconds; client.py:52 now treats it as ms, so requests time out after 30 ms"; "`ui/Cart.tsx:12` imports `db/client`, and `ui/` is bundled for the browser per CLAUDE.md:41". If the best you can write is "someone might later…" or "the reader is briefly puzzled", drop it. The exception is a hard written rule whose doc gives no rationale and for which you can find none: the rule, the breaking line and the sanctioned alternative are then enough, at `yellow`.
7. **Apply the shrug test.** Drop it when the duplication is under ~10 lines, the simplification removes no branch, state or concept, the code matches how its neighbours already do the same thing, the type could be tighter but nothing produces a wrong value, the prose is imprecise but not false, you had to read the rule generously to make it apply, or the honest comment would begin with "I would have…" or "while you're here". Those are opinions, and consistency with neighbours beats your preference. Small is not the same as opinion: a confirmed defect of little consequence goes on to step 9.
8. **One finding per root cause, anchored on a changed line, with a small concrete fix.** An old flag name surviving in three docs is one finding listing all three; five debug prints are one finding anchored on the first; one cast with several victims is one finding. Name the helper to call, the lines to delete or the corrected sentence. Use `suggestion` only when the replacement fits inside `line..end_line` and needs no new import. Unchanged stale text is anchored on the changed code line that falsifies it, with the stale text's `path:line` in `body` and `suggestion` left empty; an unchanged type declaration is never a valid anchor.
9. **Score honestly, then cut to the budget.** A `self_confidence` of 80+ needs the counterpart, the prior state and the step-3 checks each backed by a cited line. `self_importance` (0-100, defined in the contract) is a separate question: how much it matters if the author ignores the finding, given that it is true. A finding that passed every step above but matters little is still reported, as `yellow` with a low `self_importance`; low-scored findings are handled cheaply downstream, so honesty costs nothing and inflation spends a verifier. Do not inflate title, severity or score to earn a finding its place, and do not treat a low score as a licence to pad: something that fails the steps above is not a minor finding, it is not a finding. If you hold more than 6, keep the 6 with the strongest counterparts, without letting one noisy group crowd out a confirmed finding from another. If you hold more than three, run step 7 over each again, because that many from this lens usually means the bar slipped.

## False positives specific to this lens

- **Incidental or deliberate similarity** (maintainability). Two blocks look alike but change for different reasons (per-platform variants, DTOs for different APIs, handlers for distinct events), or the copy is intended (services that must not depend on each other, a vendored snippet, a frozen copy inside a migration or versioned handler). Ask: if the rule in one changed, would the other necessarily have to change too?
- **The "existing helper" is not usable here.** It handles edges differently, is deprecated, is async where this is sync, or lives in a layer this module must not import. Read the helper body and check the dependency direction before recommending it.
- **"Unused" that is required or wired indirectly.** Callback and interface signatures, overrides, framework hooks, `_`-prefixed parameters, serializer fields, symbols exported for consumers or tests, flags staged for a rollout the brief mentions. A public library symbol has users you cannot see.
- **Legitimate output and seams.** `print`/`console.log` in CLIs, scripts, build tooling and examples; debug-level logger calls; an interface with one production implementation plus a test fake; a TODO with a ticket or owner. Shorter is not simpler: a dense one-liner replacing an explicit loop is not an improvement.
- **Loose by design** (types). DTOs, wire types, ORM rows, config structs, protobuf messages, and `any`/`interface{}`/`Object` in generic plumbing such as loggers, serialisers and middleware. Only a finding when they flow unvalidated into logic that assumes more. `unknown` is the safe choice; do not flag it.
- **"This should be a union / newtype / enum / readonly" with no misuse in the change.** If the repo uses plain string ids everywhere, one more is consistent with convention. Report the actual swap or unhandled value, never the missing abstraction.
- **Casts and ignores that are already justified.** `as Foo` after a type guard or schema parse, `cast()` after `isinstance`, `map.get(k)!` right after `map.has(k)`, an ignore comment carrying a written reason (unless the reason is factually wrong about the code), `any` narrowed to something stricter, annotations added to previously untyped code, and partial objects with casts in tests (`{} as User`).
- **History and generated docs** (docs). Old changelog entries, migration guides ("before 2.0 …"), ADRs and versioned docs describe the past on purpose; typedoc/Sphinx/cobra output, OpenAPI emitted from annotations, `--help` snapshots and README regions between generated markers have their source of truth elsewhere. Check the heading or header the passage sits under.
- **Not false, so not a finding.** A hit for `timeout` or `--output` that belongs to another command (confirm through the section heading or import path); pseudo-code and placeholder values, judged only on the names this change touched; "about 5 minutes" for 270 s; comments that explain why rather than what; prose that can reasonably be read in a way that is still true.
- **Missing docs, wording, grammar, typos, comments that restate code.** A new parameter without documentation is outside this lens unless existing text became false because of it ("takes no options"). The one exception is a typo inside a command, flag, path or URL that makes copy-paste fail.
- **Inferred, unmeasurable or process rules** (conventions). "Keep functions small" and "write clean code" name no threshold, so no line objectively breaks them; a code sample in a doc illustrates one point and its incidental choices are not rules; "run the tests before committing" is addressed to an agent at work, even when written as "always". Report only what the rule's sentence literally covers.
- **Formatting and local naming, even when the doc mentions them.** Indentation, quotes, import order and the names of locals and private helpers cost nothing downstream, and the verifier scores them as nits. A written naming rule counts only for names other code or tools key off: file names, exported symbols, routes, database columns, config keys, event names.
- **Pattern policing without a licence.** No "follow existing patterns" clause in a doc means no consistency finding. With the clause, you still need at least three siblings doing it one way, no competing second pattern, and a structural rather than cosmetic difference.
- **Wrong doc, dead rule, matched context.** A nested doc from a sibling package or a personal file (`CLAUDE.local.md`) does not govern this path; a rule mandating a helper that no longer exists, or contradicted by another doc of equal specificity, is a docs defect that predates the change; a file that already breaks the rule throughout its untouched lines makes the change a match to context (hard safety rules excepted). Mention these in `notes`, not as findings.
- **Declared follow-ups and deviations.** The brief says the docs land separately, names the rule and gives a reason for departing from it, or relaxes a rule as the stated purpose of the change. The human reviewer already knows; write one line in `notes`. Dangerous docs and hard safety rules (auth, secrets, PII, applied migrations) are still reported, with the author's reason quoted in `body`.

## Severity guide

Almost everything this lens finds is `yellow`: a real defect with a bounded cost to whoever trusts the code, the type, the sentence or the rule. On its own this lens should almost never block a merge.

`red` is rare and needs a confirmed, concrete failure on a realistic path, written out in `scenario`: the defect is already a live failure, or it leads someone who trusts it faithfully into one. The consequence makes a finding red, not the strength of the rule or how much the code bothers you:
- A type lie that makes a caller pass the wrong unit or argument: `timeoutMs` now consumed as seconds while an untouched caller passes 30000; a new call site passing `(orgId, userId)` to `(userId, orgId)`, both `string`, so the permission check runs against the wrong tenant; `req.body as PaymentWebhook` letting an optional `amount` reach the ledger insert.
- A doc that tells users to run a destructive or exposing command: `prune --help` still says "asks for confirmation" after this change removed the prompt; an upgrade note added here calls a column-dropping down-migration lossless; README says tokens are masked after this change logs full request headers. Confirm the destructive path end to end in code first.
- A maintainability defect that is already a live failure: a new `dryRun` parameter that is never read while a caller in this change passes `dryRun=true` to a function that deletes; scaffolding that changes behaviour or leaks (`if (true) return cached;`, `console.log(session)`).
- A hard safety rule broken with its incident attached: a request body logged, under "never log request bodies", on an endpoint that receives credentials; an applied migration edited; or that rule softened in the same change that breaks it.

When the red consequence belongs to another lens (`security`, `correctness`), the contract's off-lens rule sets `category`.

`yellow` examples:
- A new exported function with zero references; a helper left behind after its last call was replaced; a 40-line retry loop reimplementing `lib/retry`; a config key nothing consumes; `getOrder()` that creates the order when missing, with no caller misled so far; a stray `debugger` on a server path.
- The new `'refunded'` status renders as "Unknown" through an existing formatter's `default`; a bare `# type: ignore` hides a real `Optional` mismatch that raises a clear `AttributeError` on an uncommon input.
- Docstring says "returns `null` when missing" and the function now throws; README documents `--output-dir` after the rename to `--out` with no alias; `.env.example` still lists `DB_URL` after the code switched to `DATABASE_URL`.
- Raw `console.log` where the doc mandates the structured logger; `ui/` importing `db/` against a written layering rule; a new env var missing from `.env.example` where the doc requires it; a lint rule switched off beside the code it would have caught.

Not defects, so not reported — and kept out of `notes` too, since `notes` is shown to the author as the green-light line and an opinion there reads as a finding that skipped verification: naming taste, function or file length, "could extract a helper", duplication of a few lines, obvious magic numbers, loop-vs-functional preference, a lone interface, "prefer readonly/final", missing newtypes, illegal states with no producer, missing docs, wording, comments that narrate the change, soft preferences with no drop-in alternative, one deviation amid mixed practice, formatting, anything tooling already reports. A confirmed defect that simply matters little is not on this list: it is `yellow` with a low `self_importance` (Confirm step 9).

## Cheapest proof

Searches, `git log` and `git show` are read-only, so run them yourself and put what they returned in `evidence`. Anything that edits a file or executes project code is for the verifier: describe it in `test_idea` as one command or one tiny test, saying which result confirms the finding and which refutes it. The verifier may not be allowed to execute code either (fork PRs), so lead with a proof that works by reading or searching. Most findings from this lens need nothing to run; then write "read-only: compare <path:line> with <path:line>" so the verifier does not spend an execution on it.

- **Dead code / ignored parameter:** a whole-word search that returns only the definition (`git grep -nw normalizeSku -- . ':!*.md'`); for the verifier, "delete the parameter and run the type-check and the module's tests — still green means nothing depended on it", or call the function with the flag on and off and assert the results differ (today they are identical).
- **Duplication:** a differential test feeding one table of inputs (empty, boundary, non-ASCII) to both implementations. Equal results mean the helper is a safe replacement; unequal results name the input on which the copies have already drifted. Cheaper still: swap in the helper and run the file's existing tests.
- **Misleading name:** read-only when the write or mutation is one visible line; otherwise a test asserting what the name promises — row count unchanged after `getUser(unknownId)`, argument not mutated after `isExpired(x)`.
- **Type lie / escape hatch:** build the wrong value through the public path and make one assertion on the victim — "`POST /webhook {"id":"x"}` (no `amount`) should return 400; currently 200 and a ledger row with NULL amount"; call through the new call site with distinguishable values (`user='u1'`, `org='o1'`) and assert which one the callee receives; pass the new variant to the existing formatter and assert it does not take the default branch. Static alternative: a three-line snippet that builds the wrong value and still type-checks, paired with the victim line.
- **Stale docs:** `git grep -n "output-dir" -- "*.md" docs/` hits README.md:41 while `git grep -n "output-dir" -- src/` returns nothing; `git show <base>:src/client.py | grep -n timeout` shows the text was true before this change. Runnable second choice: the documented command prints "unknown option", or the pasted example raises `TypeError`.
- **Convention:** prove both halves. The rule predates the change: `git show <base>:CLAUDE.md | grep -n "<distinctive phrase>"`. The violation is new: `git show <base>:<path> | grep -c "console\.log"` returns 0. The rule is alive: `git grep -c` counts of the banned and the sanctioned form, e.g. 2 files vs 140. Companion missing: `grep -n "NEW_VAR" .env.example` prints nothing. Misplaced file never runs: show the runner's glob (`testMatch`, `testpaths`) and that the new path does not match.
