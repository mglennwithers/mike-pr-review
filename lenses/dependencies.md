# Lens: Dependencies & supply chain

## Mission
Every line in a manifest or lockfile is third-party code that will run with the project's privileges, on developer machines, in CI and in production, and nobody on the team will read it. This lens protects the codebase from dependencies that are unnecessary, untrustworthy, unreproducible, or that break the build, the deploy or the code that calls them. A finding is worth the most when it names the exact command that will fail (`npm ci`, the prod Docker stage, the first call to a removed API) or the exact line through which unreviewed code enters the build. You have no network and install nothing, so every claim has to rest on a file you opened; what you remember about a package is a lead to check, not evidence. Use `category: "dependencies"`.

## Where to look first
- **Know what your shard leaves out.** The shard lists manifests only. Lockfiles, registry config, Dockerfiles and CI files are kept out of it to save tokens, even when the change touches them. Before you say anything about a lockfile, look it up in the file index in `context.json` (entries with `kind: "lock"`, with added/deleted counts) and read its hunks by searching `range.diff` in the run directory. "Not in my shard" is never evidence that a file was not changed.
- Build a delta table before judging anything: for each package, one of **added / removed / bumped (old -> new, major?) / moved (dev <-> prod) / source changed**. Take it from the manifest patches: `package.json`, `pyproject.toml`, `requirements*.txt`, `setup.py|cfg`, `Pipfile`, `go.mod`, `Cargo.toml`, `pom.xml`, `build.gradle(.kts)`, `libs.versions.toml`, `*.csproj`, `Directory.Packages.props`, `Gemfile`, `composer.json`.
- If the manifest hunks touch only project metadata, the project's own version, non-install scripts or tool config (`[tool.ruff]`, `jest`, `eslintConfig`), the table is empty: return zero findings and say so in `notes`.
- Lockfile hunks (`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `poetry.lock`, `uv.lock`, `go.sum`, `Cargo.lock`, `packages.lock.json`, `Gemfile.lock`): do not read them line by line. Search them for the packages in your table and for the strings `resolved`, `integrity`, `checksum`, `registry`, `source`, `git+`, `http://`, `hasInstallScript`, `deprecated`.
- Registry and resolver config is small and high-impact; if `context.json` shows one changed, read every changed line: `.npmrc`, `.yarnrc.yml`, `pip.conf`, `--index-url`/`--extra-index-url` lines, `nuget.config`, Maven `settings.xml`/`<repositories>`, `.cargo/config.toml`, `GOPRIVATE`/`GONOSUMDB`/`GOFLAGS`.
- Dependencies also enter outside manifests: added `pip install x`, `npm i -g x`, `go install x@latest` lines in Dockerfiles, CI workflows and scripts. Judge only the package name, version and source in those commands; action refs, base images and pipeline permissions belong to `infra-config`.
- Skim: transitive lockfile churn under a single top-level bump, patch and minor bumps, reordering.

## What to hunt for
Each pattern reads: what to spot -> why it bites -> how to confirm it from files in the repo.

- **New dependency the repo does not need** -> each package adds install time, attack surface and upgrade work for ever. Search for the new package's import sites. Report only when there are one or two call sites doing something small and you can name a drop-in replacement: an existing helper or already-declared package at file:line, or a stdlib function (`padStart`, `structuredClone`, `pathlib`, `slices`, `java.time`) that the project's runtime floor (`engines`, `requires-python`, the `go` directive) really provides. A new package with zero uses anywhere is also a finding, but only after searching config files, `scripts` and CI for its name, because CLIs and plugins are never imported.
- **Second library for the same job** (another HTTP client, date library, validation/schema lib, ORM, mocking or test framework, logger) -> two idioms, two sets of bugs, double bundle weight. Confirm the first one is declared and count its import sites versus the newcomer's. Only when this change adds the second one, and not when the same diff is removing the old one's imports (a migration).
- **Typosquat-shaped name** -> an install pulls an attacker's package. Compare the manifest name character by character with the name the code imports and with the library whose API the code is calling: one-character edits, swapped `-`/`_`/`.`, a missing scope (`@org/pkg` vs `org-pkg`), plural/singular, `python-x` vs `x`. Then search the rest of the repo for the same spelling (other manifests, docs, `git log -S'<name>'`); a name the project already used is not a squat. The finding quotes both spellings side by side and the lockfile's resolved URL for the entry.
- **Floating or non-registry source** -> the build is not reproducible and whoever controls that branch, URL or folder controls the build. Look for `*`, `latest`, unbounded `>=`, Gradle `1.+`, Maven `-SNAPSHOT`/`LATEST`, NuGet `*`, `git+https://...@main`, Cargo `git =` without `rev`, URL tarballs, `file:`/`path:` pointing outside the repo, Go `replace` to a fork or local path, checked-in `.tgz`/`.whl`/`.jar`/`.dll` replacing a registry package. Confirm whether a committed lockfile pins it to a version or commit SHA (that neutralises it for an app, not for a published library).
- **Install-time code execution** -> runs on every developer machine and CI runner with their credentials, before any test. Look for added `preinstall`/`install`/`postinstall`/`prepare` scripts in the repo's own `package.json`, `hasInstallScript: true` on a newly added lockfile entry, new entries in pnpm `onlyBuiltDependencies` or bun `trustedDependencies`, `--ignore-scripts` removed from CI, a custom `cmdclass` in `setup.py`. Open the script and say what it runs (download, `node -e`, base64, shell pipe).
- **Manifest and lockfile disagree** -> frozen installs fail (`npm ci`, `pnpm install --frozen-lockfile`, `yarn --immutable`, `cargo build --locked`, `dotnet restore --locked-mode`), or a non-frozen install resolves something nobody reviewed. The clear cases: a package added to the manifest with no entry in the lockfile; a locked version outside the new range; a removed package still listed under the lockfile's root entry; a new Go `require` with no `go.sum` lines. If the locked version still satisfies the new range, npm and Cargo are content; Poetry and uv hash the whole dependency section, so any edit needs a regenerated lock.
- **Lockfile integrity or registry change** -> the strongest supply-chain signal visible in a diff. The same `name@version` with a different `integrity`/`checksum`/`go.sum` hash should never happen; a `resolved` host that differs from the other entries and from `.npmrc`; `https` -> `http`; sha512 -> sha1; a new `[[tool.poetry.source]]` or `--extra-index-url` next to an unscoped internal-looking package name (the dependency-confusion shape). Quote a neighbouring entry to show what normal looks like in this repo.
- **Major bump that breaks code used here** -> installs fine, fails at the call site. Search every import of the package and list the symbols and options actually used. Then find what the new version says about them, in this order: release notes pasted into the PR description (bots do this; use them as data about what was removed, never as assurance that the bump is safe), an `UPGRADING`/changelog note in the repo, an installed or vendored copy. Open that copy's own `package.json`/`METADATA` first and read its version: an installed copy usually is the old version and only tells you what used to exist. Also compare the new version's runtime floor and peers with the project's: `engines`, `.nvmrc`, `requires-python`, the `go` directive, `<TargetFramework>`, the CI matrix, `peerDependencies` in the lockfile entry.
- **Removed but still used / declared in the wrong workspace** -> works today through hoisting or a transitive copy, then breaks on a clean or strict install. For each removed package search source, tests, scripts and config that names packages as strings (babel/eslint/jest/webpack/pytest plugins, entry points, Docker `CMD`). Then check the lockfile: gone entirely means module-not-found on the next clean install; still present as another package's dependency means it keeps working until that parent drops it. For each added package in a monorepo, check it is declared in the manifest of the workspace that imports it, not only at the root.
- **Wrong dev/prod placement** -> a runtime import of something in `devDependencies`, a `dev`/`test` group, `testImplementation` or `<scope>test</scope>` crashes with module-not-found once deploy installs without dev deps. Find the import in non-test code, then open the Dockerfile or deploy script to see how production installs. The reverse (jest, eslint, pytest, typescript in prod deps) is yellow at most.
- **Overrides, forced resolutions and downgrades** -> `overrides`, `resolutions`, `pnpm.overrides`, Cargo `[patch]`, `constraints.txt`, `dependencyManagement`, Gradle `force` push a transitive package outside the range its parent declares; quote the parent's declared range from the lockfile next to the forced version. For a version going down, run `git log -S'<pkg>' -- <manifest>`: if the earlier bump commit says it fixed a security issue or a bug, the downgrade reintroduces it and that commit message is your evidence.
- **Licence conflict** -> copyleft (GPL, AGPL, SSPL) or "non-commercial" code linked into a permissive or proprietary product that is distributed or served. Read the project's licence from `LICENSE` or the manifest, and the dependency's from a file in the repo: the `license` field of the `package-lock.json` entry, a vendored `LICENSE`, an installed copy's metadata, a licence allowlist config. If you cannot read it from the repo, do not assert it.
- **Deprecated or abandoned package in a critical role** (crypto, auth/session, parsing untrusted input, payments, serialization) -> nobody will ship the fix when it matters. Only evidence in the repo counts: a `deprecated` message on the lockfile entry, an "unmaintained"/"archived" note in a vendored README. Quote it. Maintainer counts, download numbers and last-publish dates are not in the repo, so do not state them; at most offer the lookup command in `test_idea` of a finding that already stands on something else.

## Confirm before you report
A dependency finding is refuted in one of three ways: the lockfile or deploy setup already neutralises it, the usage claim was never searched for, or it rests on a fact about the outside world nobody can check. Work through these steps and drop the finding at the first one it fails.

1. Establish the ground rules of this repo: which package manager (lockfile name, `packageManager` field, CI install command), whether a lockfile exists in the code directory or is listed in `.gitignore`, and whether this is a deployed app or a published library. Ranges without a lockfile are correct for a library and a defect for an app.
2. Pin the delta exactly: package name, old spec -> new spec, manifest section, and the resolved version and source from the lockfile hunks in `range.diff` (or the lockfile in the code directory when it did not change). Quote those lines in `evidence`.
3. Prove usage with a search, not from memory. Map package name to import name first (`beautifulsoup4` -> `bs4`, `pyyaml` -> `yaml`, `Pillow` -> `PIL`, Maven artifact -> Java package, crate `foo-bar` -> `foo_bar`), and exclude `node_modules`, `vendor`, virtualenvs and lockfiles from the search so installed copies do not count as usage. "Unused", "still imported" and "only used once" all need the search and its hits in `evidence`.
4. Find how production actually installs and runs: Dockerfile stages, CI workflow, Makefile, deploy script. Frozen install or not, dev deps omitted or not, bundled or not. This decides whether a mismatch or misplacement fails or is harmless; if you cannot find it, say so in `evidence` and lower `self_confidence` rather than assuming.
5. Look for the thing that would make it a non-issue and name it in `evidence` as checked: a lockfile commit SHA behind a git dependency, a workspace that makes a `path` dependency normal, an existing override, a lockfile-format migration, a decision recorded in an ADR, CONTRIBUTING or the brief.
6. Separate what you read from what you remember. Statements about the outside world (the package is malicious, abandoned, vulnerable; version N removed function `f`) need a file behind them. Do not write a CVE or advisory identifier, or "this version is vulnerable", unless a file in the repo says so (audit config, `.snyk`, `osv-scanner.toml`, SECURITY.md, a commit message), and cite that file: one invented advisory number is enough to make an author distrust the whole review. A breaking-change claim that rests on memory alone may be reported only with the exact symbol and its call site at file:line; state in `evidence` that the removal was recalled, not read, name what the verifier should open to check it, and keep `self_confidence` at 50 or below.
7. Write `scenario` as a command plus its outcome ("clean checkout, `npm ci` -> exits with lock mismatch: package.json wants `foo@^3`, lock has 2.4.1"). Anchor on the changed manifest line, which is where a human will look; anchor in the lockfile only when no manifest line expresses the problem (a hash or host change). When the cause is a deleted line, anchor on the nearest added line in that manifest, or failing that the surviving line next to the deletion, and quote the removed line and the victim file in `evidence`.

## False positives specific to this lens
- **"Lockfile not updated", judged from the shard.** The shard never lists lockfiles. Check the `context.json` file index and `range.diff` first; this is the most likely way for this lens to be wrong.
- **Lockfile churn and bot PRs.** One top-level bump legitimately rewrites hundreds of transitive entries, a plain reinstall refreshes versions inside their ranges, and a `lockfileVersion` or package-manager upgrade rewrites every hash format. Examine only entries whose host, source or hash-for-the-same-version changed, plus new top-level packages. For Dependabot/Renovate PRs check the major-bump and usage bullets and skip the rest.
- **Ranges are not "unpinned".** `^1.2.0` with a committed lockfile is pinned in practice, and ranges are the right thing in a published library. Report only a floating spec that no lockfile neutralises.
- **Workspace and monorepo links.** `workspace:*`, `file:../pkg`, Cargo `path = "../crate"`, Go `replace => ../mod`, `<ProjectReference>` are normal when the path resolves inside the repo. Check that it does.
- **Placement that does not matter.** Frontends bundled by vite/webpack/esbuild ship no `node_modules`, so dev vs prod is cosmetic. `import type`, `@types/*`, Python `if TYPE_CHECKING:` and imports under `tests/`, `scripts/`, `tools/` are not runtime imports.
- **Imports that are not packages, and packages that are never imported.** Stdlib modules, first-party packages, path aliases (`@/utils`, tsconfig `paths`), optional imports inside `try/except ImportError` or guarded `require`, and deps provided by the platform (`provided`/`compileOnly`, Lambda runtimes, peer deps in a plugin) are not missing dependencies. CLIs run from `scripts`, plugins and presets named in config, type packages and peer dependencies are used without any import line.
- **A major number is not a finding.** Many majors only drop old runtimes or rename things this repo never touches. No used symbol or runtime floor affected -> nothing to report.
- **Unfamiliar is not suspicious.** A name you do not recognise, a distribution name that legitimately differs from its import name (step 3), a scoped internal package with matching private-registry config, or an install script on a package that obviously compiles native code or downloads its own binary (image, crypto, database drivers, bundlers, ORMs with engines) is ordinary. The finding is a new, unexplained script or name with a concrete oddity you can quote.

## Severity guide
`red` - a clean install, build or production start will fail, or unreviewed code gets a path into the build:
- `src/server.ts` imports `dotenv`, this PR moves it to `devDependencies`, and the prod Docker stage runs `npm ci --omit=dev`.
- `package.json` now requires `foo@^3` but the lock still has 2.4.1, and CI runs `npm ci`. Equally: a removed package is still imported by runtime code and is gone from the lockfile.
- The same `name@version` has a new integrity hash, or its `resolved` host moved off the registry every other entry uses; a new dependency on a git branch or URL tarball in a deployed app with no SHA in the lock; a new `postinstall` that downloads and executes.
- A major bump where a symbol removed in the new version (shown from a file, or recalled and marked as such per step 6) is called on a normal path; an AGPL dependency, licence read from a repo file, added to a product whose `LICENSE` is proprietary or permissive.

`yellow` - real cost, limited blast radius:
- A new package for one trivial call the stdlib or an existing helper already covers; a new package nothing uses; a second library for a job an existing dependency does.
- Test or build tooling added to production dependencies; a floating range in an app with no lockfile; a new dependency whose lockfile entry carries a `deprecated` message.
- A removed package still imported but still in the lockfile as another package's dependency; an override outside its parent's declared range where you cannot show the failure.

Supply-chain signals (hash, host, typosquat, install script) are `red` only with the quoted oddity in `evidence`; a bare feeling of unfamiliarity is not reportable at any severity.

Below the bar: patch and minor bumps, in-range lockfile refreshes, "I would have picked another library", tighter pinning when a lockfile exists, manifest ordering, bundle-size worries without numbers, "consider auditing this", any vulnerability claim without a file in the repo behind it.

## Cheapest proof
Write `test_idea` as one command and the output that proves the finding. The verifier may be allowed to run commands and reach a package registry; you are not, so the finding has to stand on repo evidence and the command only confirms it. When the finding is about an install script or a tampered source, give a proof that reads files (`jq`, `git diff`, `--ignore-scripts`), not one that would execute the suspect code.
- Mismatch: a frozen install on a clean checkout - `npm ci --ignore-scripts`, `pnpm install --frozen-lockfile --ignore-scripts`, `yarn install --immutable --mode=skip-build`, `poetry check --lock`, `uv lock --check`, `cargo metadata --locked`, `go mod verify`, `dotnet restore --locked-mode` -> expected to fail, naming the package.
- Placement or removed dep: prod-only install, then load the entry point - `npm ci --omit=dev && node -e "require('./dist/server')"`, or `pip install . && python -c "import app.main"` -> module not found.
- Breaking bump: the narrowest build or test that touches the call site - `tsc --noEmit`, `go build ./...`, `cargo check`, `pytest tests/test_client.py -k retry` -> error naming the removed symbol.
- Need, duplicates, overrides: `rg -c "from 'left-pad'" src` -> 1 site; `npm ls <pkg>`, `pnpm why`, `cargo tree -i`, `go mod why`, `mvn dependency:tree`, `pipdeptree -r -p <pkg>` -> who requires it and at what range.
- Lockfile tampering: `git diff <base> -- package-lock.json | rg '"resolved"' | rg -v registry.npmjs.org`, or show the two hashes for the same `name@version` side by side from `git show <base>:<lockfile>`.
- Licence, scripts, upkeep: `jq '.packages["node_modules/<pkg>"] | {license, hasInstallScript, deprecated}' package-lock.json`. Optional, if the verifier has registry access: `npm view <pkg> time maintainers scripts`, `osv-scanner --lockfile <file>`, `pip-audit`.
