# Lens: Concurrency & async

## Mission

Protect the codebase from defects that only appear when two things happen at once, or in an order the author did not picture: lost updates, double-processed jobs, deadlocks, leaked tasks, work that silently never finishes. These bugs pass every sequential test and every read-through, then surface in production as unreproducible corruption or hangs. A finding from this lens is worth something only when it arrives with the exact interleaving that breaks things — a named interleaving gets fixed; "possible race condition" gets ignored, and rightly.

Two families live here, and they are confirmed differently (see the checklist): **races**, where two actors interleave on something shared, and **async-structure defects**, where work is never awaited, bounded, cancelled or joined.

## Where to look first

Before judging anything, establish the execution model once per changed file, because the same code is safe in one model and broken in another: single-threaded event loop, thread-per-request, prefork worker processes, goroutine-per-connection, actor mailbox? Then find how many copies run: server flags (`--workers`, `--threads`, `WEB_CONCURRENCY`), the Procfile or Dockerfile `CMD`, Kubernetes `replicas` and CronJob `concurrencyPolicy`, queue worker concurrency (Sidekiq, Celery, BullMQ, SQS batch settings). Cite what you found in `evidence`; if the repo does not say, record that as an assumption instead of guessing silently.

Then rank changed hunks by how much concurrent machinery they touch:

1. Lines that create concurrency: `go`, executor/thread submits, `Task.Run`, `asyncio.create_task`/`gather`, `tokio::spawn`, `Promise.all`, queue consumers, cron/scheduled jobs, `setInterval`, webhook and message handlers.
2. Lines that touch shared mutable state: module/package-level variables, singletons, static fields, in-memory caches and maps, files at fixed paths, DB rows that are read and then written back.
3. Lines that add or move synchronisation: locks, `synchronized`, semaphores, channels, atomics, transaction boundaries, `SELECT ... FOR UPDATE`, isolation settings, retry wrappers, Redis/DB lease locks.
4. Changed async structure: a function that became async (or stopped), a callback converted to a promise, new timeouts, contexts or cancellation tokens.
5. Lines the change deleted: a removed lock, `await`, `FOR UPDATE`, transaction wrapper, dedupe check or `ctx` argument. Read the `-` lines of the patch as carefully as the `+` lines. Deleted lines cannot carry a finding, so anchor on the nearest added or modified line that now runs unguarded and quote the deleted line in `body`.

Skim: pure functions over local data, request-scoped objects that never escape the request, one-shot CLI scripts, markup, config. Read tests only to learn what concurrency the author already exercised; flaky tests belong to the tests lens.

## What to hunt for

- **Check-then-act / read-modify-write on in-process state** — `if k not in cache: cache[k] = build()`, `count += 1`, `if (!map.containsKey(k)) map.put(k, v)`, a lazy singleton initialised without `sync.Once`/`volatile`/a lock. Two actors both pass the check and one update is lost or the build runs twice. Confirm: find the second actor and the window — under threads any two callers suffice; on an event loop there must be an `await`/yield between check and act (look inside callees too).
- **Read-modify-write, exists-then-insert and job claiming on DB rows** — `SELECT balance` → compute in app → `UPDATE SET balance = ?`; "find or create" without a constraint; `SELECT ... WHERE status='pending' LIMIT 1` then `UPDATE`, so two workers claim the same job. Wrapping it in a transaction does not help at READ COMMITTED (the Postgres default), nor for a plain SELECT-then-UPDATE under MySQL REPEATABLE READ. Confirm: open the schema/migrations for a unique index; look for `FOR UPDATE` (`SKIP LOCKED` for claims), a version column, an atomic `SET x = x + ?`, an upsert, or a guarded transition (`UPDATE ... WHERE status='pending'` plus a rows-affected check).
- **Missing await / floating work** — an async result dropped so errors vanish and the caller proceeds early: `forEach(async ...)`, `map(async ...)` without `Promise.all`, a Python coroutine called without `await` (it never runs), an `asyncio.create_task` result not retained (the loop holds only a weak reference), C# `async void` or an unawaited `Task`, a Rust future created and never polled. Confirm: open the callee to verify it really is async and can fail; check that what follows depends on completion (response sent, commit, file closed, test assertion); check whether `no-floating-promises` or an equivalent runs in CI — if it does, drop it.
- **Unbounded fan-out** — `Promise.all(items.map(fetch))`, `gather(*tasks)`, a goroutine per item with no limit, over input whose size a user or the data controls: exhausts sockets, the DB pool, memory or a third-party rate limit. Confirm: trace the collection to its source and cite what caps it (page size, schema `maxItems`, a `LIMIT`) or that nothing does; search the repo for an existing limiter (`p-limit`, semaphore, `errgroup.SetLimit`, worker pool) the author should have used. A `Promise.all` whose siblings keep writing after the first rejection is reportable here only when the caller then retries or rolls back the batch, so the stray writes are duplicated or orphaned; otherwise the errors lens owns partial failure.
- **Sequential await in a loop that should be parallel** — reportable only when all three hold: the iterations are independent, n realistically reaches the hundreds (cite where n comes from), and a user or a timeout is waiting on the result. Two or three straight-line awaits belong to the performance lens.
- **Lock held across I/O or await; blocking the scheduler** — `mu.Lock()` then an HTTP/DB call; a Rust `std::sync::Mutex` guard alive across `.await`; a DB transaction or row lock held open across an external API call; `threading.Lock`, `time.sleep` or a sync HTTP client inside `async def`; sync-over-async (`.Result`, `.Wait()`, `runBlocking` on a request thread, `block_on` inside a runtime). Every caller queues behind the slowest call, and the blocking variants deadlock or starve the pool. Confirm: read the whole critical section to the release, including callees, and cite the slow call inside it.
- **Lock ordering, missed release, lease locks** — new code takes B while holding A; find any path that takes A while holding B (the same applies to two transactions that update the same rows in opposite order, e.g. transfer A→B vs B→A). A `return`/throw between acquire and release with no `defer`/`finally`/`using`. A Redis/DB lease lock whose TTL can expire before the work finishes, or that is released with a plain delete so it removes another holder's lock. Confirm: search every acquisition site of both locks and write the two orders down; for leases, compare the TTL with the slowest call inside.
- **Reentrancy and self-overlap** — a method that re-acquires a non-reentrant lock (Go `sync.Mutex`, Rust `Mutex`, Python `Lock` vs `RLock`), or invokes a user callback/event emitter while holding it; `setInterval(async ...)` or a scheduled job whose run can outlast its period, so two runs process the same rows; a submit/click handler that starts the same async mutation twice with no in-flight guard. Confirm: compare the realistic run time with the period (or find the second trigger) and look for an in-flight flag, single-flight helper or scheduler overlap setting.
- **Non-thread-safe collection shared across threads** — a Go map written from several goroutines (fatal "concurrent map writes": a crash, not a glitch), `HashMap`/`ArrayList`/`SimpleDateFormat` in a singleton bean, C# `Dictionary`/`List` in a static, iterating a Python dict while another thread mutates it. Confirm the sharing, not the type: open the DI registration or constructor call site to establish the owner's lifetime (singleton vs per-request).
- **Goroutine / task leak** — a spawned worker blocks forever on a channel send because the receiver returned early (timeout, error, first-result-wins); background tasks never joined or cancelled at shutdown; `setInterval`, listeners or subscriptions added on a per-request or per-render path and never removed. Confirm: enumerate every exit path of the receiver and check the sender can still complete on each (buffered channel of sufficient size, or `select` on `ctx.Done()`).
- **Channel and WaitGroup misuse** — close by the receiver or by one of several senders (double close and send-on-closed both panic), `range` over a channel nobody closes, unbuffered send with no guaranteed receiver, `wg.Add` inside the goroutine (so `Wait` can return first), loop variable captured by a goroutine when `go.mod` declares Go < 1.22. Confirm: identify the single owner of `close` and count the senders.
- **Cancellation and timeouts not propagated** — a new outbound call uses `context.Background()`, omits the `AbortSignal`/`CancellationToken`, or has no timeout while the caller has one in scope; a `Promise.race`/`wait_for` timeout that abandons the work without cancelling it; a broad catch that swallows `CancelledError`, `OperationCanceledException` or `InterruptedException`, making the task uncancellable. Confirm: name the context/token that is in scope on the changed lines and not passed, and open where the client is constructed for a default timeout.
- **Non-idempotent handler under redelivery** — queue consumers, webhooks, cron on several replicas, client or proxy retries, a retry wrapper newly placed around a non-idempotent call. The side effect (charge, email, insert, increment) happens before or without recording a dedupe key; ack-before-work loses jobs, work-then-crash-before-ack duplicates them. Confirm: read the delivery semantics in config (retry count, visibility timeout, ack mode); look for an idempotency key, a unique constraint on the event id, `ON CONFLICT DO NOTHING`, or a status guard.
- **Filesystem TOCTOU** — `exists()` then `open`/`mkdir`/`unlink`; a fixed temp path; read-modify-write of a shared file with no lock or atomic rename. Confirm that two processes can actually overlap (two workers, overlapping cron runs, parallel CI jobs); the fix is exclusive create (`O_EXCL`, mode `'x'`) or write-temp-then-rename. If the path is attacker-influenced, report it with `category` set to `security`.
- **Event-ordering assumptions** — code assumes arrival order equals send order: webhooks (`updated` before `created`), a partitioned queue without a partition key, two in-flight responses where the last to resolve wins (typeahead, a React effect with no cleanup/abort overwriting newer state). Confirm: look for what enforces order (partition key, sequence/version comparison, abort of the prior request). If nothing does and the handler overwrites unconditionally, it is real.
- **Transaction scope and isolation assumptions** — an external side effect (publish, enqueue, email, API call) inside a DB transaction before commit: the consumer reads a row that is not yet visible, or the transaction rolls back and the effect cannot. An ORM session/`DbContext`/transaction client shared across concurrent tasks (`Promise.all` over queries on one transaction). Isolation newly raised to SERIALIZABLE/REPEATABLE READ with no retry on serialization failure, so ordinary contention becomes user-facing errors. Confirm: find the real transaction boundary — it is often a decorator, middleware or `with` block outside the hunk — and the isolation level actually configured.

## Confirm before you report

Work through these in order. Each step either produces a file:line for `evidence` or kills the finding. Steps 2–3 apply to races and step 4 to async-structure defects; everything else applies to both.

1. **Name what is contended or abandoned.** For a race: exactly which variable, row, file, channel or lock, and its lifetime (process-global, per-instance, per-request). If it is created per call and never escapes, stop. For an async-structure defect: exactly which promise, task, goroutine or lock hold, and the line that should have awaited, joined, bounded, cancelled or released it.
2. **Races — prove two actors.** Identify two concrete execution contexts that reach the changed line at the same time — two requests on a thread pool, two worker replicas, a retry plus the original, a timer and a handler — and cite where each one starts. For cross-process races, cite the config that gives more than one process. "Could be called concurrently" with no caller that does so is speculation.
3. **Races — find the window.** Point to the suspension or preemption point between check and act: an `await`, a blocking call, any statement under preemptive threads, the gap between two SQL statements. No window, no race.
4. **Async-structure defects — prove the trigger.** Cite the line that makes the defect fire: the `throw`/reject inside the un-awaited callee, the receiver's early-return path that strands the sender, the uncapped source of the fanned-out collection, the deadline in scope that is not passed down, the slow call inside the lock. A floating call that cannot fail and that nothing downstream depends on is not a finding.
5. **Hunt for the existing guard.** Before writing anything, look for: a lock taken by the caller (`fooLocked` naming, "caller must hold mu" comments), a unique index or constraint, `FOR UPDATE` or a version column, a framework serialisation guarantee (actor mailbox, per-key queue, single consumer, unique-job plugin, scheduler overlap policy), a dedupe table, an in-flight flag, a limiter around the fan-out, a framework that awaits the returned promise. List every place you checked in `evidence`. The verifier looks here first; a guard you missed is the most common refutation.
6. **Write the interleaving.** Put it in `scenario` as ordered steps with labelled actors and line numbers: "T1 reads stock=1 (L42); T2 reads stock=1 (L42); T1 writes 0 (L47); T2 writes 0 (L47) → two orders filled from one unit." For async defects, give the event order: "handler returns 200 at L30; `sendEmail` rejects at L28 with nothing observing it → unhandled rejection terminates the Node process." A finding whose steps you cannot write out is not ready; read more or drop it.
7. **State the consequence in domain terms and its plausibility.** What ends up wrong (double charge, lost write, one stuck goroutine per timed-out request, process crash) and how often (every provider retry vs. a sub-millisecond window on an admin page). The consequence sets severity, not the pattern.
8. **Say what the diff contributed.** Name the ingredient this change supplies: the second writer, the `await` inside the window, the retry wrapper, the removed lock, the new replica count or schedule. Code that was moved or re-indented with the same unsynchronised access contributes nothing.

Score `self_confidence` at 80+ only when steps 1–6 each rest on a line you read. If the actors or the absence of a guard rest on an assumption (no deployment config in the repo, the schema lives elsewhere), say so in `evidence` and score 50–65 — the verifier can often settle it cheaply, but only if told what to check.

## False positives specific to this lens

- **Event loop with no suspension in the window.** JS, asyncio and Redis scripts run check-and-act atomically unless something awaits in between. Read the callees before claiming a race.
- **Deliberate or framework-handled un-awaited work.** `void p`, an attached `.catch(log)`, `ctx.waitUntil(...)`, a background task with its own try/catch, a promise returned (not awaited) to a framework or test runner that awaits it. Report only when errors go unobserved or the caller's correctness depends on completion.
- **The guard lives elsewhere.** A unique constraint with the conflict handled, a lock held by the caller, Rust `&mut self` (exclusivity is compiler-enforced), prefork servers where "globals" are per-process, actors and per-key queues, a worker pinned to concurrency 1, a CronJob with `concurrencyPolicy: Forbid`, leader election.
- **Already the concurrent primitive.** `sync.Map`, `ConcurrentHashMap`, atomics, `Interlocked`, a channel used as the hand-off — check how it is used (compound check-then-act on a concurrent map is still a race), but the type alone is not a finding.
- **Compile-time guarantees.** Data races in safe Rust do not compile, and structured-concurrency scopes (Kotlin, Swift, Python `TaskGroup`) cancel and join children themselves. Logic races, deadlocks and lost updates in those languages are still fair game.
- **Thread-confined data.** A plain `HashMap` that is a local, lives on a per-request object, or sits in a `ThreadLocal`/`contextvars` slot is not shared, however unsafe the type.
- **Naturally idempotent handlers.** A redelivered event that sets an absolute value (`SET status='paid'`), upserts by the event's own key, or overwrites a cache entry does no harm. Redelivery matters for increments, inserts, sends and charges.
- **Sequential await that is sequential on purpose.** Order matters, each iteration feeds the next, the API is rate-limited, or the calls share one transaction/connection that cannot multiplex. Suggesting `Promise.all` there introduces a bug.
- **Benign races.** Two actors computing the same cache value where last-write-wins is harmless; approximate metrics counters. (A Go map is never benign — concurrent writes crash.)
- **Runs once, alone.** Startup/init before serving, migrations, one-shot scripts, test setup and dev tooling — unless the init itself spawns workers that share what it is still building.

## Severity guide

`red` — a realistic interleaving corrupts data, moves money twice, crashes, deadlocks or leaks without bound:
- Lost update on a balance, inventory or quota via read-modify-write under ordinary concurrent traffic; two workers claiming and executing the same job.
- A webhook or queue handler that charges/emails/inserts with no dedupe, where the provider retries on timeout.
- A Go map written from HTTP handlers; a lock-order inversion between two request paths; sync-over-async that can exhaust the request thread pool.
- A removed `await` that lets the response or commit happen before the write, or drops its errors; a goroutine leaked on every timed-out request on a hot path.

`yellow` — real, but the failure is contained or the path is rare:
- A duplicate insert that the constraint rejects but the code surfaces as a 500 instead of handling the conflict; serialization failures with no retry.
- Unbounded fan-out over input that is capped today but hits an external rate limit at the cap; a timeout that abandons expensive work or a pooled connection without cancelling it.
- A lock held across slow I/O that limits throughput without deadlock; a task leak on a rare error path; a stale-response overwrite in a UI; a scheduled job that overlaps itself only under unusual load.

Below the bar: "use a concurrent collection" with no second thread; races that need two admins in the same millisecond and end harmlessly; parallelising small-n or batch loops; mutex-vs-channel preferences; missing timeouts where a client default exists; cheap work that merely continues after a client disconnects; "make this idempotent" for handlers that are never redelivered.

## Cheapest proof

You do not run any of this — the lens only reads. `test_idea` is a recipe for the verifier, so make it one that forces the interleaving instead of hoping for it: name the function, the two actors, the barrier point and the assertion. "Add a concurrency test" is not a test idea. In rough order of preference:

- **Deterministic barrier.** Stub the I/O inside the window with a latch or deferred promise so both calls pass the check before either acts: "Call `reserve(item)` twice under `Promise.all` with `db.getStock` mocked to resolve only after both calls started; expect one rejection; currently both succeed and stock is -1."
- **N-parallel hammer.** 50 concurrent calls, then assert the invariant (counter == 50, exactly one row, no exception). In Go, a two-goroutine test under `go test -race -run TestX -count=20 ./pkg/...` turns a maybe into a certainty.
- **Duplicate, overlapping or reordered delivery.** Invoke the handler twice with the same event id and assert the side effect happened once (mock call count or row count); start a second run of the job before the first resolves; deliver `updated` before `created` and assert the final state.
- **Floating work.** Make the callee reject and assert the caller's promise rejects; or lint the one file with `@typescript-eslint/no-floating-promises`; in Python run the test with `-W error::RuntimeWarning` to catch "coroutine was never awaited".
- **Leak or deadlock.** `goleak.VerifyNone(t)` after driving the timeout path, or compare `runtime.NumGoroutine()` before and after 100 timed-out calls; `jest --detectOpenHandles`; for deadlock, two threads released by a latch into the two paths under a 2-second test timeout.
- **Database.** Two `psql` sessions: `BEGIN; SELECT` in both, `UPDATE` in both, `COMMIT` both, show the final value. Or simply `\d table` to show the unique index is absent.
- **Fan-out bound.** Call with 10k items against a mock that records maximum in-flight calls; assert it stays under the intended limit.
