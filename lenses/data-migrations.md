# Lens: Data & migrations

## Mission

Protect production data and the deploy that touches it. Schema and data changes are the one kind of change that cannot be fixed by reverting the commit: a dropped column is gone, a locked table is an outage while the migration runs, and a migration that aborts halfway blocks every deploy behind it. A finding from this lens tells the author exactly which statement fails or destroys what, against which existing rows or which still-running code version, before they learn it in production. Use `category: "data-migrations"`.

## Where to look first

- **Migration files first** (`db/migrate/`, `migrations/`, `alembic/versions/`, `prisma/migrations/`, `*.sql` under a versioned dir, Flyway `V*__`, Liquibase changelogs, EF `Migrations/`). Read each one statement by statement; for ORM DSLs, write down the SQL it will emit for the project's engine, because the finding is about that SQL, not the DSL.
- **Then three to five sibling migrations already on main.** They tell you the house style: whether `down`s are kept, whether the team already uses concurrent index builds, batched backfills or expand/contract steps. A new migration that departs from an established safe idiom is a much stronger lead than one that merely could be safer.
- **Then model/entity/schema definitions** changed in the same diff (`models.py`, `schema.prisma`, `@Entity` classes, `schema.rs`, Ecto schemas, sqlc queries). Pair each model change with its migration and each migration with its model change — an unpaired one is a lead.
- **Then code that persists structured data outside the schema**: cache values, queued job payloads, session blobs, JSON columns, event-store records, search-index mappings. Shape changes here are migrations nobody wrote.
- **Then how migrations are run**: CI/CD workflow, `Procfile` `release:`, Helm hooks, container entrypoints, app-startup auto-migrate. You need this to argue any deploy-order finding.
- Skim only: schema dumps and snapshots (`schema.rb`, `structure.sql`, EF `ModelSnapshot`) — they mirror the migration, so anchor on the migration, not the dump — and seeds, fixtures, factories and test-only DB setup.

## What to hunt for

- **Blocking or rewriting DDL on a populated table.** Postgres `CREATE INDEX` without `CONCURRENTLY`, `ALTER COLUMN TYPE`, `ADD COLUMN` with a volatile default, `ADD FOREIGN KEY`/`CHECK` without `NOT VALID` + later `VALIDATE`, `SET NOT NULL` (full scan under `ACCESS EXCLUSIVE`); MySQL `ALTER` that cannot run `ALGORITHM=INPLACE/INSTANT`. Writes queue behind the lock and the app times out. This is only a finding once checklist steps 1 and 2 hold.
- **Statement that cannot run inside the runner's transaction — or that loses atomicity outside it.** Most runners wrap each migration in a transaction, and Postgres refuses `CREATE INDEX CONCURRENTLY` there (and `ALTER TYPE … ADD VALUE` before 12; from 12 the new value cannot be used in the same transaction), so the migration fails every time. Look for the opt-out: Rails `disable_ddl_transaction!`, Django `atomic = False` with `AddIndexConcurrently`, Alembic `autocommit_block()`, Knex `config = { transaction: false }`, Flyway `executeInTransaction=false`, EF `suppressTransaction: true`. Conversely, once the opt-out is set, every other statement in that file runs unprotected: a column add or backfill sharing the file with the concurrent index is left half-applied when a later statement fails.
- **NOT NULL without a default or backfill.** On existing rows the statement errors (Postgres) or silently writes an implicit zero/empty value (MySQL non-strict, SQLite). Separate trap: an ORM-side default is not a database default — SQLAlchemy `default=` vs `server_default=`, and Django drops the DB default after `AddField` — so old code still inserting during a rolling deploy hits a NOT NULL violation. Name the writer that omits the column: the previous code version, a raw SQL insert, another service, an import job.
- **Column/table dropped or renamed while deployed code still uses it.** During a rolling deploy old code runs against the new schema, and a rename is a drop from the old code's point of view. ORMs that list columns explicitly fail on every read of that table (Django, Hibernate, SQLAlchemy); ActiveRecord's cached column list fails on every write — not just the queries that use that column. If the reader removal and the drop land in the same PR, that is the defect: it needs expand → deploy → contract. Search the new tree for the old name in code, raw SQL, views, triggers, serializers, reports and sibling services.
- **Rename or move that the tool emitted as drop + add.** Autogenerators often cannot see a rename (Alembic autogenerate, Prisma, TypeORM, sometimes EF and Django `makemigrations`) and write `DROP COLUMN old` + `ADD COLUMN new`, which discards every existing value. The same applies to a column moved to another table with no copy step between the add and the drop. Compare the model diff (a field renamed) with the migration (a drop and an add of the same type) and look for the missing `RENAME` or `UPDATE … SET new = old`.
- **Lossy type change.** `varchar(255)`→`varchar(50)`, `bigint`→`int`, `numeric`→`float`, `timestamptz`→`timestamp`, text→enum, an enum value removed, JSON→typed column via cast. Either the migration fails on the first out-of-range row or the data is silently truncated. Show that such values exist or can exist: model/form/API validators with the old limit, a `USING` clause that maps unknowns to NULL, enum values still written by code that the new type omits.
- **Unique / FK / check constraint added over data that may already violate it.** The migration aborts mid-deploy. Violations are likely when uniqueness was only enforced by an application validator (racy), when comparison semantics differ (case, whitespace, NULLs), or when soft-deleted rows share the key (needs a partial index). Check whether a dedupe/cleanup step runs first and whether it covers those cases.
- **Backfill or data fix that is wrong, unbatched, or in the deploy path.** Read the `WHERE` first: an `UPDATE`/`DELETE` that matches more rows than the stated intent, or mishandles NULL, corrupts data irreversibly. Then the mechanics: a single `UPDATE big_table SET …` in the DDL transaction holds the lock for its full duration and can exceed the release-phase timeout (Heroku release, Helm `--timeout`, a liveness probe killing an auto-migrating pod into a crash loop); a batch loop terminates only if the update falsifies the batch predicate; rows written between backfill and constraint need a default or dual-write; and a migration that uses live application models (Rails `User.find_each`, Django importing the model rather than `apps.get_model`) breaks when that model later changes.
- **Down migration missing where the project keeps them, or present but wrong.** A wrong `down` is worse than none: it drops a column the `up` did not create, recreates a column without its data/type/default/index, or leaves `up` non-repeatable after rollback. Check Django `RunPython` without `reverse_code`, `RunSQL` without `reverse_sql`, Rails `change` containing non-reversible ops (`remove_column` without a type, `execute`).
- **Model and migration drift.** Model changed with no migration, or they disagree: nullability, default, length, index/unique declared on one side only, enum value added in code but not in the DB enum or check constraint, EF migration without the updated `ModelSnapshot`, `schema.prisma` vs `migration.sql`, generated query code (sqlc, jOOQ, Diesel `schema.rs`) not regenerated. Open both sides and compare field by field. If the migration is missing, anchor on the changed model line.
- **Editing a shipped migration, or broken ordering.** Checksum-validating runners (Flyway, Liquibase, sqlx; Prisma in `migrate dev`) reject the edited file; others (Rails, Django, Alembic) silently never re-run it, so environments diverge. Confirm with `git log` that the file existed on the main branch before this change. Also compare against main's current migration list: a version/timestamp older than one already on main where the runner rejects out-of-order, two Alembic heads, or two Django leaf migrations in one app.
- **Not idempotent / unsafe under partial failure.** MySQL and Oracle auto-commit DDL, so a multi-statement migration that fails at step 3 cannot be re-run without `IF [NOT] EXISTS` guards. Data migrations and seeds that `INSERT` without an existence check or `ON CONFLICT` duplicate rows when re-run or when run on every startup. Startup-time "ensure schema" code added by this change and executed by several replicas at once needs an advisory lock.
- **Money and time in lossy types.** New or retyped columns/fields using `float`/`double`/`real` or a JS `number` of fractional currency for amounts; `DECIMAL` with no scale (MySQL defaults to `(10,0)`); zone-less `timestamp`/`DATETIME` written from zone-aware values or from naive local time. Trace the value from computation to storage and back, and show the line where precision or the offset is lost.
- **PII and sensitive data handled outside the repo's own convention.** A new column for SSN/DOB/token/address stored plaintext when sibling columns use an encryption or hashing helper; a data migration that logs row contents or copies PII into an analytics, audit or history table that the deletion/anonymisation job does not cover. Find the existing convention first (encrypted-field helpers, log filters, erase jobs) and show that the new data skips it. Use `category: "security"` when a secret or credential is exposed.
- **Persisted shape changed without a version bump.** Cached objects, job payloads, session blobs, pickled classes, Avro/proto records, search mappings: a field renamed or made required while the cache key, payload version or index alias stays the same means new code deserialises old entries (and old instances read new ones during rollout). Find the key construction and TTL, then open the reader and check what it does with a missing or extra field — a reader that tolerates both is not a finding.

## Confirm before you report

Not every step gates every finding. Steps 1-2 gate anything about locks, constraints, backfills or narrowing on existing rows; steps 3-4 gate anything about one code version meeting the other version's schema or payload; steps 5-7 apply to all. Drift, an edited shipped migration, drop + add data loss and a wrong `down` need neither a big table nor a rolling deploy — do not drop them for lack of either.

1. **Pin the engine, version and runner.** Read DB config, `DATABASE_URL` scheme, Prisma `provider`, driver dependencies, docker-compose images. Locking and transactional-DDL behaviour is engine-specific, so cite what you found in `evidence`. If you cannot determine the engine, do not report an engine-dependent finding.
2. **Show that existing rows are at stake.** Required: the table's `CREATE` is in a migration already on main — find it and cite it. If the table is created in this PR or belongs to a feature that has not shipped, stop. For a constraint, NOT NULL or narrowing finding one conflicting row is enough, so show how such a row can exist (step 7). For a lock-duration finding you need a size signal, because the repo cannot give you row counts. Strong: earlier migrations on this table already use the concurrent or batched idiom; the code batches, paginates, partitions or archives it; docs or comments state its volume. Weak: a core or append-heavy entity by name (users, orders, events, audit) or many FKs pointing at it. Weak signals alone mean `yellow` with `self_confidence` ≤ 60; no signal means no finding.
3. **Establish deploy order.** Find where migrations run relative to the code rollout. Migrate-before-rollout (the common case) means old code meets new schema; migrate-after means new code meets old schema. A deploy that stops the app before migrating removes these findings; a single instance that migrates and then restarts has a window of seconds, which is `yellow` at most. If the repo does not show how it deploys, say so in `evidence`, keep the finding only when you see signs of more than one instance (replica counts, a load balancer, health-checked rollout, sibling migrations written expand/contract style), and cap `self_confidence` at 60. For client-side databases (mobile, desktop, embedded SQLite) the concern shifts to users upgrading across several versions at once.
4. **Enumerate readers and writers.** Search the new tree for the affected table/column/key in ORM attributes, raw SQL strings, views, triggers, serializers, admin/reporting code, factories, and other services in a monorepo. Name the surviving reader or writer with file:line. For a same-PR drop, the "surviving reader" is the base commit's code — cite the removed line. If every search comes back clean and the removal shipped earlier, there is no finding.
5. **Look for the safety net that makes it moot.** `strong_migrations`, `safe-pg-migrations`, squawk, `django-migration-linter`, `atlas lint` in CI; online schema-change tooling (gh-ost, pt-osc, pg-osc); a migration helper that sets `lock_timeout`. If CI already lints this pattern, CI owns it. A `safety_assured { }` block with a stated reason is the justified silencing the contract describes; one without a reason is not.
6. **Check history.** `git log --follow -- <migration>` against the main branch: a file new in this PR may be edited freely; one already on main may not. For a drop, check whether the reader removal landed in an earlier release, or the column was already hidden from the ORM (Rails `ignored_columns`, Django `SeparateDatabaseAndState`) — that is a correct contract step.
7. **Write the scenario as a timeline or a concrete row.** "T0 release phase runs `ALTER TABLE orders DROP COLUMN legacy_status`; T1 old instances still serving run `SELECT … legacy_status …`; every orders read 500s until rollout completes", or "existing rows `email='A@x.com'` and `'a@x.com'` → `CREATE UNIQUE INDEX … lower(email)` fails with 23505". If you cannot name the statement and the pre-existing state it collides with, keep reading or drop it. Give `self_confidence` ≥ 80 only when engine, existing data and the failing statement are all cited.

## False positives specific to this lens

- **Table created in the same PR or unreleased migration series.** No rows, no lock, no backfill; NOT NULL, unique and plain `CREATE INDEX` are all fine. Verify that the `CREATE TABLE` is in this diff.
- **Small or static tables** (lookups, plans, feature flags, settings). The lock lasts milliseconds, so lock-duration findings do not apply; a constraint that existing rows violate still does.
- **The engine does not have the problem.** Postgres 11+ adds a column with a constant default without a rewrite; nullable `ADD COLUMN` is metadata-only; Postgres 12+ skips the `SET NOT NULL` scan when a validated `CHECK (col IS NOT NULL)` exists; MySQL 8 has `INSTANT`; CockroachDB, Spanner and Vitess do online schema changes. Postgres DDL is transactional, so partial-failure arguments apply to it only where the migration opted out of the transaction.
- **Forward-only projects.** A missing `down` is not a defect when the sibling migrations have none either, or the tool has no such concept (Prisma, Flyway community, plain sqlx).
- **The framework already handles it.** Django `AddField(default=…)` backfills existing rows; Rails `add_index algorithm: :concurrently` with `disable_ddl_transaction!`; `IF NOT EXISTS` guards; Liquibase preconditions. This is why you write down the emitted SQL before asserting what happens.
- **The brief explains it.** "Contract step for the column ignored in the last release", "runs in a maintenance window", "table is empty in production" are claims, not instructions: check them against history and deploy config (steps 3 and 6). If they hold, there is no finding; if the repo contradicts them, say how.
- **Generated artefacts and non-production scripts.** Schema dumps, snapshots, seeds, fixtures, dev-only reset scripts. Do not double-report a migration finding on its dump, and do not call column-ordering noise in a dump "drift".
- **Floats and naive timestamps that are fine.** Ratios, scores, coordinates and measurements are legitimately floating point; a codebase that consistently stores UTC in zone-less columns is following a convention. Report only when money or instant semantics are demonstrably involved and the change departs from how sibling columns do it.
- **PII by column name alone.** A column called `email` is not a finding. It becomes one when the repo protects comparable data and this change bypasses that, or the diff writes the value to logs or analytics.

## Severity guide

`red` — the deploy fails, data is lost or corrupted, or a realistic outage:
- Column dropped in the same PR that removes its last reader, with migrate-before-rollout and more than one instance: old instances error on reads or writes to that table until the rollout completes.
- A rename emitted as drop + add with no copy step; a data-fix `UPDATE`/`DELETE` whose `WHERE` matches rows it should not; `numeric(12,2)` → `float` on ledger amounts; a `down` that drops a column holding data the `up` did not create.
- `SET NOT NULL` or a unique index on a pre-existing table with no backfill/dedupe and a nameable conflicting row; `CREATE INDEX CONCURRENTLY` inside the runner's transaction; an edited migration under a checksum-validating runner.
- A non-concurrent index or table rewrite on a table with a strong size signal (step 2).

`yellow` — real, but fails safe or has limited blast radius:
- The same lock or unbatched-backfill pattern where table size rests on weak signals only; a same-PR drop on a single instance that migrates and then restarts.
- `RunPython` without `reverse_code` in a project whose other migrations are reversible; backfill using live model classes; unrelated statements sharing a file whose transaction is disabled.
- Model says non-nullable, migration creates the column nullable (drift that errs on the permissive side).
- Cache shape changed without a key bump where the reader tolerates it but serves the stale shape until TTL; a new zone-less timestamp in a codebase that otherwise uses `timestamptz`.

Below the bar: migration naming and file layout, column order, "consider adding a down" in forward-only projects, index suggestions with no query in the diff that needs one (performance lens), preferring one migration idiom over an equivalent one, missing comments.

## Cheapest proof

`test_idea` is a recipe for the verifier, who may run code when you may not. Name one command and the exact pre-existing state, and never require production data. The two `git` commands below are read-only, so run them yourself and put the output in `evidence` instead. Pick the matching shape:
- **Constraint/NOT NULL/narrowing:** "Scratch DB: migrate to the parent revision, insert `<one concrete violating row>`, apply this migration → expect `<error>` (or read back the truncated value)."
- **Drop + add data loss:** "Scratch DB at the parent revision, insert one row with `old = 'x'`, apply this migration, `SELECT new` → NULL/default instead of `'x'`."
- **Reversibility:** "On an empty scratch DB run up → down → up and diff the schema dump against a plain up."
- **Drift:** `python manage.py makemigrations --check --dry-run`, `alembic check`, `prisma migrate diff --from-migrations … --to-schema-datamodel … --exit-code`, `dotnet ef migrations has-pending-model-changes`, or `rails db:migrate && git diff --exit-code db/schema.rb`.
- **Locking / transaction wrapping:** `squawk <file.sql>` or `atlas migrate lint`; `python manage.py sqlmigrate <app> <nnnn>` (or the runner's dry-run/`--sql` mode) to show the emitted SQL and whether it sits inside `BEGIN`.
- **Deploy order:** the exact search that finds the surviving reader, e.g. `git grep -n "legacy_status" <base-sha> -- ':!db/migrate'`; or "load the base commit's model against the new schema and run one `SELECT`".
- **Shipped migration edited:** `git log --oneline origin/main -- <migration path>` returning commits proves the file had already shipped.
- **Idempotency:** "Run the data migration/seed twice; assert the row count is unchanged."
- **Money/time:** "Store `1234567.89` (or `0.1 + 0.2`) through the new column and read it back"; "store a zone-aware instant, read it back under a different session time zone, compare."
