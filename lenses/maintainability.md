# Lens: Maintainability & simplicity

## Mission

Protect the codebase from changes that work today but set a trap for the next person: logic that now lives in two places, a helper reinvented next to the real one, parameters and flags that do nothing, names that promise one thing and do another, scaffolding that was never removed. A finding from this lens (`category: "maintainability"`) is worth something to the author only when it names a specific counterpart ("this already exists at X", "this copy already differs from that one at Y", "nothing reads this") and a small, safe fix.

This lens is the one most prone to nitpicking, and two contract exclusions run straight through its territory: naming/style, and hypothetical future problems. Both still apply here. A name is reportable only when the behaviour contradicts it, not because a better name exists. Duplication or complexity is reportable only with a cost you can show in today's code, not because "someone might later…". The bar is what a senior engineer on the team would hold the merge for or push back on hard; most changes produce nothing from this lens.

## Where to look first

- **New units of logic**: new files, new functions over ~15 lines, new classes. For each ask three questions: does this already exist somewhere? is every input actually used? does the name match the body? Most real findings come from these three.
- **Changed signatures and config surfaces**: new parameters, boolean flags, options objects, env vars, config keys, feature flags. These are where "accepted but ignored" hides.
- **Hunks that resemble each other** inside the diff, and new code in or near `utils/`, `common/`, `helpers/`, `shared/`, `lib/` — the likeliest places for a twin to exist already.
- **Call sites the change replaced**: when a call to a helper, flag or config key is swapped for something else, check whether that was its last use.
- **New types with one user**: interfaces, base classes, factories, generic parameters, registries added alongside a single implementation.
- Skim only: generated and vendored code, lockfiles, snapshots, fixtures, migrations, docs, and one-line fixes. In test files look only for leftover debug scaffolding; repetition in tests is usually deliberate.
- Pure moves and renames show old warts as added lines. Before judging a large added block, check whether it was moved (`git log --follow`, `git show -M --stat`, or search the deleted lines of the diff for its first line).
- Spend your searches on the two or three largest new pieces of logic rather than spreading thin across every hunk.

## What to hunt for

- **Duplicated logic that will drift** — the change pastes or re-derives a business rule (pricing, permission check, validation, state transition, format parsing) that already lives elsewhere, or adds two copies itself. The next fix lands in one copy and the other silently keeps the old behaviour. Reportable when the copy is substantial (roughly 10+ lines of real logic, not boilerplate) and one copy must change whenever the other does; strongest when the copies already disagree on some input. Confirm: search the repo for distinctive literals, error strings, field names and magic numbers from the new block; open the twin; compare line by line and note each difference. Cite both locations.
- **Reimplementation of something already available** — hand-rolled retry/backoff, debounce, deep clone, chunking, slugify, date parsing, URL or path building by string concatenation, group-by, when the repo has a helper or the stdlib/an existing dependency covers it (`itertools`, `Object.fromEntries`, `slices.Contains`, `Collectors.groupingBy`, `Path.Combine`, `str::split_once`). Hand-rolled versions miss edge cases the shared one already fixed. Confirm: look at what sibling files import for the same job, search helper directories by verb, check the manifest for a dependency already present, then read the helper body to make sure it really is equivalent. Never recommend adding a new dependency from this lens.
- **Dead code introduced or orphaned by the change** — a new function, class, export, constant, file or branch that nothing reaches; or an existing helper, flag or config key whose last use this change replaced while leaving the definition behind. It gets maintained, misleads readers about what the system does, and often signals an unfinished wiring job. Confirm: search the symbol repo-wide, including string forms, re-exports, DI/route/plugin registration and templates. For an unreachable branch, show the condition that makes it so. For an orphan, anchor on the added or modified line that replaced the last use; if the use was simply deleted and there is no changed line to anchor on, leave it.
- **Parameter, flag or option that does nothing** — accepted but never read, read but with no effect on any output or side effect, a config key or env var added to the schema and never consumed. Callers believe they are controlling something. Confirm: read the whole function body and everything it forwards the value to; check whether an interface, override or callback signature forces the parameter; open each caller to see what it passes and what it expects to happen.
- **Name says X, code does Y** — `getUser` that inserts, `isValid` that mutates or throws, `validate` that normalises and returns a different value, `timeoutMs` fed seconds, `sortedItems` never sorted, `safeHtml` that does not escape, inverted booleans (`disableCache=true` enabling it). Callers code against the name, so the mismatch becomes a bug at the call site. Confirm: find a caller — ideally one in this change — that relies on the promised meaning, and quote it. With no such caller, report only the forms that mislead whoever calls next: a read-sounding name (`get`, `is`, `has`, `find`, `validate`) on a body that writes, sends or mutates its argument, or a unit, ordering or polarity stated in the name that the body contradicts. Anything softer is naming taste, which the contract excludes.
- **One function, unrelated jobs** — a function that gains a second responsibility behind a mode flag with disjoint branches, a getter/constructor/query that now writes or sends, validate-persist-notify in one body sharing mutable locals. Bugs arise when a change to one job disturbs the other. Confirm: point to the shared variable or ordering dependency between the halves, or to a caller that needs only one half and triggers the other as a side effect. Length alone is not a finding.
- **Needless complexity with a clearly simpler equivalent** — flag-and-loop where a stdlib call exists, `new Promise(async (resolve) => …)` around an already-async call, `try/except` that only re-raises, a state machine for two states, manual index arithmetic over a slice, a wrapper class that only delegates, nesting four deep that guard clauses flatten. Report only when you can write the simpler form in a few lines, it removes a branch, a piece of state or a concept, and you can argue it is equivalent on the edges.
- **Speculative generality** — a factory, strategy, registry, plugin hook, generic parameter or option bag added with exactly one implementation and one caller, so a reader hops through two or more new indirections to reach one concrete behaviour. Confirm: search for implementers and callers (including test doubles); check the brief and PR description for a stated follow-up; check that neighbouring features are not built the same way. A lone interface with one implementation is not enough — it has to be machinery you can show collapsing to a direct call.
- **Abstraction inversion and layer leaks** — in non-test code: a low-level module importing from a higher layer (util importing handlers), domain code taking the HTTP request object, reaching past a facade into private internals (`obj._field`, another package's `internal/`, reflection on private members), parsing the string output of the project's own formatter instead of using the structured value. Confirm: trace the import cycle this creates (A imports B at `path:line`, B imports A at `path:line`), or show that no sibling in the same layer imports upward, so this change is the first to cross the boundary. If siblings already do it, the boundary is not real here.
- **Hand-synchronised parallel structures** — the same set enumerated in several places (enum members in a switch and again in a map, fields in a serializer and again in a validator) where the change adds a member to one and not the others, or hand-copies an existing list it could import or derive. Confirm: search for an existing member's name to find every enumeration and list each `path:line`; say which one the change missed. If the missed place produces wrong behaviour now, that is a `correctness` finding.
- **Copy-paste residue** — a pasted block still carrying the source's identifiers: an error message naming the wrong function, a metric or log key from another feature, a variable from the original context that happens to be in scope. This is duplication that has already bitten. Confirm: open the source block and show the stale token next to the correct one.
- **Leftover debug code and scaffolding** — `console.log`, bare `print`, `dbg!`, `fmt.Println`, `System.out.println`, `debugger`, `breakpoint()`, `pdb.set_trace()`, `binding.pry`, `if (true)` / `if False:` short-circuits, an early `return` added for testing, hard-coded localhost URLs, test IDs or sleeps. Confirm: check how the rest of the file logs (project logger vs. print) and whether stdout is the program's actual output.
- **Ownerless TODO/FIXME/HACK added by the change** — report only when it marks missing behaviour on a reachable path ("TODO: handle pagination", "FIXME: not thread safe") with no ticket, owner or mention in the brief. Wish-list TODOs are below the bar. Confirm: the path is live and the unhandled case can occur; name the input that reaches it.
- **Commented-out code added by the change** — three or more lines of a disabled old implementation or alternative left in place. Readers cannot tell whether it is meant to come back, and it rots against refactors; history already preserves it. A single commented-out *call* also counts when it silently switches off a check, a cleanup or a notification that used to run — report that under the lens that owns the consequence. Confirm: it is code rather than an explanatory example.

## Confirm before you report

1. **Rule out moved code.** A block relocated verbatim (same body in the diff's deleted lines, or a rename in `git show -M --stat`) was not written in this change, even though every line shows as added. Drop findings about its content.
2. **Produce the counterpart.** Every finding here needs a second reference: the other copy, the existing helper, the caller that is misled, the simpler form — or, for "nothing uses this", the exact searches you ran and what they returned. A finding with no counterpart `path:line` is an opinion and the verifier will refute it.
3. **Argue equivalence on the edges.** For "use the existing helper" and "simpler equivalent", walk empty, null/None, zero, negative, non-ASCII, timezone, error and ordering cases through both versions, and check sync vs. async, laziness, short-circuit evaluation and mutate-vs-copy. If they differ, either the difference is the point (say which behaviour is right and why) or the finding is dead.
4. **Rule out invisible users.** For dead code and unused parameters, search for the name as a string and check reflection, decorators, DI containers, route tables, serializer field names, templates, `__all__`/public exports, interface or override requirements, build tags and tests. A public library symbol is used by people you cannot see.
5. **Check whether tooling already says it.** Unused locals, imports, private functions and parameters, and unreachable code are often caught by the compiler or a lint rule (`noUnusedLocals`/`noUnusedParameters`, `no-unused-vars`, ruff/flake8 `F`/`ARG` rules, `unused`/`unparam` in golangci, `dead_code` in Rust). Open the lint config and the CI workflow; if the rule is enabled and CI runs it, the contract says drop it. What tooling cannot see — an unused export, a config key nobody reads, a flag read but without effect — stays yours.
6. **State the cost in the present tense.** Write `scenario` as something checkable now: "api/import.py:88 passes `strict=True` and gets no strictness because L40-71 never read it"; "invoice.ts:52 rounds half-up, export.ts:117 truncates: 10.005 shows as 10.01 on screen and 10.00 in the CSV"; "the same 30-line eligibility rule is at a.go:40 and b.go:112, and `git log` shows a.go:40 edited four times this year". If the best you can write is "someone might later…", read more or drop it.
7. **Apply the size test.** Drop it when: the duplication is under ~10 lines or a single expression; the simplification saves lines but removes no branch, state or concept; the pattern matches how the surrounding code already does the same thing; or the honest review comment would start with "nit" or "while you're here". Consistency with neighbours beats your preference.
8. **Make the fix small and concrete, and merge by root cause.** Name the helper to call, the lines to delete, or show the simpler form (three lines at most) in `body`. Use `suggestion` only when the replacement fits inside `line..end_line` and needs no new import. Five stray debug prints are one finding anchored on the first, listing the rest. Give `self_confidence` of 80+ only when steps 2-4 are backed by cited lines. If you end up with more than three findings, run step 7 over each again — that many from this lens usually means the bar slipped.

## False positives specific to this lens

- **Incidental similarity.** Two blocks look alike but change for different reasons (per-platform variants, DTOs for different APIs, handlers for distinct domain events, test setup). Ask: if the rule in one changed, would the other necessarily have to change too? If not, it is not duplication.
- **Deliberate duplication.** A comment, the brief or the repo layout says the copy is intended: separate services or packages that must not depend on each other, a snippet vendored to avoid a dependency, a frozen copy inside a migration or versioned API handler.
- **The "existing helper" is not usable here.** It handles edges differently, is deprecated, is async where this is sync, or lives in a layer this module must not import. Read the helper and its tests, and check the dependency direction, before recommending it.
- **"Unused" that is required or wired indirectly.** Callback and interface signatures, overrides, framework hooks, `_`-prefixed parameters, serializer fields, symbols exported for consumers or tests, flags staged for a rollout the brief mentions.
- **Shorter is not simpler.** A dense one-liner, nested ternary or clever reduce replacing an explicit loop is not an improvement, and neither is removing an abstraction that names a real concept. `if c: return True else: return False` is a nit, not a finding.
- **Seams that exist for a reason.** An interface with one production implementation plus a fake or mock in tests, a DI boundary at an I/O edge (clock, HTTP client, database), or the pattern every neighbouring feature already follows (builder per entity, interface per service, explicit mappers). One more instance of a local convention is not a finding.
- **Legitimate output and logging.** `print`/`console.log` in CLIs, scripts, build tooling and examples; structured logger calls at debug level; `fmt.Println` in `main` of a command. Check what the file's neighbours do.
- **TODOs with a ticket, owner or date, and follow-ups listed in the brief.** Also comments that contain code as documentation (usage examples, before/after notes) rather than disabled code.
- **Generated or vendored code**, and private-member access inside tests.

## Severity guide

Default to `yellow`; this lens on its own should almost never block a merge. Use `red` only when the maintainability defect is already a live failure — and then set `category` to the lens that owns the failure (`correctness`, `security`).

`red` examples:
- New `dryRun` parameter is accepted and never read, and a caller in this change passes `dryRun=true` to a function that deletes records.
- Leftover scaffolding changes behaviour or leaks data: `if (true) return cached;`, `console.log(session)` printing tokens, a hard-coded test endpoint on the production path.
- Two copies of a rule introduced or touched by the change already disagree on a realistic input and users see both results.

`yellow` examples:
- A 40-line retry loop that reimplements `lib/retry` with no behavioural divergence yet.
- A new option or config key nothing consumes; a new exported function with zero references; a helper left behind after its last call was replaced.
- `getOrder()` that creates the order when missing, with no caller misled so far.
- A stray `debugger` or debug print on a server path; an ownerless `TODO: handle pagination` on a reachable path; a block of commented-out old implementation; a factory plus registry for a single implementation.

Below the bar, not reported: naming taste, function or file length as such, "could extract a helper", duplication of a few lines, magic numbers whose meaning is obvious in context, loop-vs-functional preference, readable ternaries, file organisation, missing comments, a lone interface, anything a compiler or CI lint rule already flags.

## Cheapest proof

Searches and `git log` are read-only, so run them yourself and put what they returned in `evidence`. Anything that edits a file or executes project code is for the verifier: describe it in `test_idea` as one command or one tiny test, stating which result confirms the finding and which refutes it.

- **Dead code / unused parameter:** a whole-word repo search that returns only the definition (`git grep -nw normalizeSku -- . ':!*.md'`); for the verifier, "delete the parameter and run the type-check and the module's tests — still green means nothing depended on it".
- **Ignored flag:** call the function twice with the flag on and off and assert the outputs or side effects differ; today they are identical.
- **Duplication / reimplementation:** a differential test feeding one table of inputs (include empty, boundary, non-ASCII) to both implementations and asserting equal results. Equal means the helper is a safe replacement; unequal names the input on which the copies have already drifted. Cheaper still: swap in the helper and run the file's existing tests.
- **Simpler equivalent:** apply the rewrite and run the existing tests for that module; for pure functions, a property test comparing old and new over generated inputs.
- **Misleading name:** a test asserting what the name promises — row count unchanged after `getUser(unknownId)`, argument not mutated after `isExpired(x)`.
- **Debug leftovers:** exercise the path and capture stdout, or search the built bundle for `debugger` / the hard-coded URL.
- **Drift and layering:** `git log --oneline -- <path of the original copy>` to show the rule changes often; `git grep -n "from app.handlers" -- app/utils` to show this is the only upward import in the layer.
