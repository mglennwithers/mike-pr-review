# Lens: Type design & invariants

## Mission

Protect the codebase from types that let a bug be written without anyone noticing: shapes that admit illegal states, invariants that hold only by convention, and escape hatches that switch the checker off on exactly the path where it was needed. A finding from this lens is worth the author's time only when it names a specific wrong value the new code can now build, accept or persist, and the place downstream where that value does damage. A type that merely could be tighter is design taste, and taste does not survive verification; what does survive uses `category: "types"`.

## Where to look first

- **New or changed type declarations**: classes, structs, interfaces, records, dataclasses, enums, ORM models, schema definitions (zod, pydantic, serde, protobuf, GraphQL). Read the whole declaration plus its constructor/factory and every mutator, not just the hunk.
- **Boundaries where untyped becomes typed**: `JSON.parse`, `json.loads`, `Unmarshal`, request handlers, env/config readers, DB row mappers, queue consumers, FFI. Casts and unvalidated assumptions cluster here.
- **Added escape hatches**: scan added lines for `any`, `as X`, `as unknown as`, postfix `!`, `@ts-ignore`/`@ts-expect-error`, `# type: ignore`, `cast(`, Go `x.(T)` without `, ok`, `interface{}`, Java/C# downcasts and raw generics, `dynamic`, Kotlin `!!`, `default!`, `unsafe`/`transmute`. A hit tells you where to start reading; it is not a finding until the checklist below holds.
- **Changed signatures and fields**: adjacent parameters of the same primitive type, reordered parameters, a changed unit or meaning (seconds to milliseconds, cents to units), a new optional field, changed nullability, a new enum variant or status value. When the change alters what an existing parameter or field means, the damage is in the call sites and readers it did not touch, so open those too.
- **Skim**: pure renames and moves, generated code (`*.pb.go`, OpenAPI clients, `*_generated.*`), vendored types, test fixtures, annotations added to previously untyped code with no behaviour change, helper types private to one function.

## What to hunt for

Each entry names a shape and then how to confirm it. The shape alone is never the finding; the confirmed producer and victim are. Entries are ordered roughly by how often they turn out to be real.

- **Checker escape on a risky path** — `as Foo` on parsed JSON or an HTTP response, `any` flowing into money/auth/persistence code, a bare `# type: ignore` or `@ts-ignore` hiding a genuine mismatch, unchecked Go assertion (panics), unchecked generic cast. The declared type becomes a lie and the failure surfaces far from its cause. Confirm: trace the value back to its source and show the source can really produce a different shape (field optional in the provider's schema or docs, nullable column, another variant) with no runtime validation in between. For an ignore comment, read the declared types on both sides of the expression to work out which mismatch it hides, then treat that mismatch as the illegal value. An ignore that carries a written reason falls under the contract's "explicitly silenced" rule; leave it alone unless the reason is factually wrong about the code (it says "validated above" and nothing validates).
- **Nullable confusion** — nullability differs between layers (nullable column, non-null model; optional in the API schema, required in the client type); this change makes a field nullable or optional while existing readers still dereference it, in a language or config where the checker does not force them to be updated (Python, Go pointers, Java, non-strict TS); `null`/`undefined`/missing/`""`/`0` mean different things but are collapsed by `||`, `or`, `?? ''`; Go zero values in a PATCH struct overwrite stored data because "absent" and "zero" are indistinguishable. Confirm: open the migration or schema and the mapper, find a row or payload that legitimately carries the null, and follow it to the dereference or the wrong write.
- **New variant nobody handles, or a stringly-typed enum** — a variant or status value added in this change, or `status: string` compared to literals in several places. Confirm: search every comparison/switch on the old values and show one where the new value falls into a `default`/`else`/silent no-op (Go `switch` with no default, Python `if/elif` chain, TS switch without a `never` check). Show what that branch then does. Consumers inside the repo are yours; strict consumers outside it belong to the `api-compat` lens.
- **Primitive mix-up that actually happens** — `(userId: string, orgId: string)`, cents vs. units, seconds vs. milliseconds, UTC vs. local, float money. Confirm: read every call site the diff adds or changes and compare argument order and units against the parameter list; check the unit at the source (a config value in seconds handed to a millisecond API). If the change reorders parameters or changes a unit, run the same comparison over the call sites it left untouched. Report the swap or mismatch, not the absence of a newtype.
- **Invariant bypassed at construction** — the type has a validating constructor or factory, and the change adds a path around it: public fields, an object/struct literal bypassing `NewX`, Kotlin `copy()` around a validating factory, pydantic `model_construct`, a derived deserialiser (`serde`, Jackson, Gson) on a type whose `new()` validates. Confirm: locate the validation, show the new path that skips it, and name the invalid value that arrives.
- **Inconsistent enforcement across mutators** — the constructor checks `start <= end`; the new setter, `withX`, `update()` or `__setattr__` path does not. Confirm: read every mutator on the type, then find a consumer that relies on the invariant (a duration that goes negative, an index that goes out of range).
- **Optional fields that are really a union** — `{kind:'card'|'bank', cardNumber?, iban?}`, a dataclass with co-required `Optional`s, a Go struct of "exactly one of" pointers. Confirm: find a construction site that omits the co-required field, or a reader that dereferences a variant field (`!`, `.get()`, default value) without checking the discriminant.
- **Boolean soup** — two or more flags, or a status plus flags (`isLoading`, `isError`, `data`), whose combinations include impossible states. It bites when a reader branches on one flag and assumes the others. Confirm: enumerate the combinations, find a writer in the change that produces an illegal one (sets `error` without clearing `data`), then a reader that mishandles it.
- **Mutable exposure of internals** — a getter returning the internal list/map/slice/`Date` by reference, a constructor storing the caller's collection without copying, a Go sub-slice sharing a backing array, a Python class-level attribute or mutable default shared across instances (skip the default-argument form if the repo's linter config flags it), shallow `readonly`/`final`. It bites when the owner caches derived state (sorted, deduped, total, size cap). Confirm: find a caller that actually mutates or retains the reference, or demonstrate the cross-instance sharing.
- **Parallel arrays / index-coupled collections** — `ids[]` with `names[]`, a map plus a separate order list. Confirm: find the change filtering, sorting or appending one without the other, then the reader that zips by index.
- **Serialization type doing a domain type's job (or the reverse)** — an ORM entity returned straight from a handler, so a new column (`passwordHash`, internal flag) ships to clients or becomes mass-assignable; an all-optional wire DTO used in business logic so each consumer invents its own default; a field renamed for domain clarity on a struct that is also cached, queued or stored. Confirm: find where the type is serialised (handler return, `Marshal`, cache set, publish) and name the field that leaks or the consumer whose default is wrong. Set `category` to `security` for a leaked or mass-assignable field and to `data-migrations` for a stored payload that no longer decodes.
- **Layer leak with a concrete failure** — a lazy-loaded entity or transaction-bound object escaping the scope that keeps it alive; a handler switching on driver-specific error codes that the second implementation (other backend, in-memory fake) never emits. Confirm: find the lifetime boundary or the second implementation and show what breaks there. Without that, it is architecture opinion.
- **Lossy representation in code** — 64-bit ids through a JS `number`, `int64`→`int32` / `long`→`int` narrowing casts, a decimal parsed into a float before arithmetic. Confirm: establish the realistic magnitude (how ids are generated, largest existing values) and point at the conversion site. Column widths and column types belong to the `data-migrations` lens.
- **Broken equality/hash for a keyed type** — a field added to a class but not to `equals`/`hashCode`/`__eq__`/`__hash__`, a mutable field in the hash, objects used as `Map`/`Set` keys compared by identity, Go pointer keys. Confirm: find the collection that keys on the type and the visible consequence (duplicates, cache never hits, lookup fails after mutation).

## Confirm before you report

1. **Name the illegal value.** Write the exact instance, state or argument the type permits and should not — `{status:'paid', paidAt:null}`, `transfer(orgId, userId)` — not "illegal states are representable". If you cannot write it down, you do not have a finding.
2. **Find the producer.** Show a path, in this change or reachable from it, that actually builds or admits that value: a constructor call, a mutator, a DB row, a deserialiser. If every writer is correct, the loose type is a design opinion. At an external boundary the producer is the outside world; then your burden is to show nothing validates between the boundary and the type.
3. **Find the victim.** Search for the type, field and function names, open the consumers, and point at the line that misbehaves with that value: the dereference, the wrong branch, the arithmetic, the persisted garbage, the leaked field. State what the user or system observes. This becomes `scenario`.
4. **Hunt for the guard you missed.** Check validation middleware and schemas (zod, pydantic, JSON Schema, Bean Validation, FluentValidation), DB constraints (`NOT NULL`, `CHECK`, enum, FK), factories, `__post_init__`/`init` blocks and framework guarantees. Then open the checker config (`tsconfig.json`, `mypy.ini`/`pyproject.toml`, `.golangci.yml`, the `.csproj`, compiler flags in the build file) for settings that already fail CI on this: `strictNullChecks`, `noUncheckedIndexedAccess`, strict mypy/pyright, exhaustiveness linters, `-Wswitch`, `<Nullable>enable`. Cite each place you checked; the verifier will look in the same places, and a guard it finds first sinks the finding.
5. **Attribute it to this change.** The changed lines must open the hole or newly route a value through an existing one. A change that uses an already-loose type the same way its neighbours do is not a finding, unless it adds the first producer of the bad value.
6. **One hole, one finding.** If one loose type or cast has several victims, report it once and list the victims in `body`. Several findings about the same `as Foo` use up the finding budget and read as noise to the author.
7. **Check the fix is proportionate.** If the remedy is local (validate in the constructor, return a copy, add the `ok` check, handle the missing case), say so in `body`. If the only remedy is a redesign across many files and you have no victim line, drop it; a redesign request without a demonstrated bug is exactly what this lens must not produce.
8. **Anchor and score.** Anchor on the changed line that opens the hole: the declaration if the change loosened it, otherwise the new cast, the new producer or the swapped call. An unchanged declaration is not a valid anchor. A `self_confidence` of 80 or more needs all three legs — producer, victim, no guard — each with a file:line. If the producer or victim is still missing after you have opened the consumers, drop the finding. The one exception is an unvalidated external boundary feeding money, auth or persistence where you could not get at the provider's schema: report it, say which leg is unproven, and score it below 60.

## False positives specific to this lens

- **Anemic DTOs, wire types, ORM rows, config structs.** They mirror an external shape and are supposed to be loose. Only a finding when they flow unvalidated into logic that assumes more.
- **"This should be a union / newtype / enum" with no misuse in the change.** If the repo uses plain string ids everywhere, one more is consistent with convention. Report the actual swap or unhandled value, never the missing abstraction.
- **Casts that follow a runtime check.** `as Foo` after a type guard, schema parse or discriminant test; an assertion inside a Go type switch; `cast()` after `isinstance`; `map.get(k)!` right after `map.has(k)`. Read the ten lines above the cast and the function that produced the value.
- **`any`/`interface{}`/`Object` in generic plumbing** — loggers, serialisers, middleware, DI containers, event buses whose consumers narrow. `unknown` is the safe choice (it forces narrowing); do not flag it.
- **Escape hatches the change did not add or loosen.** A cast on a moved line, `any` narrowed to a concrete type, annotations added to untyped code: the change made things stricter, and the looseness that remains predates it.
- **A mutable getter nobody mutates.** In internal code, require a mutating or retaining caller, or a demonstrated shared-instance bug. Exposure alone is below the bar.
- **Holes the language or repo config already closes.** In Rust, Kotlin, Swift and strict TS/C#, nullability and exhaustiveness errors fail the build, and the contract excludes anything the build catches. Check the config before claiming a null hole or an unhandled variant.
- **Framework-mandated shapes.** JPA/EF entities need no-arg constructors and setters, protobuf makes everything optional, UI state objects are plain bags. The invariant usually lives in a validator or service layer; find it before concluding it is absent.
- **Test code and fixtures.** Partial objects with casts (`{} as User`), loose mocks and builder shortcuts in tests are normal.

## Severity guide

**`red`** — the hole has a producer and a victim on a realistic path, and the result is wrong persisted data, a crash, a leak, or a wrong authorisation decision.
- `req.body as PaymentWebhook` with no schema check; `amount` is optional in the provider's payload, so `undefined` reaches the ledger insert and is stored as NULL/NaN.
- A Go PATCH struct with non-pointer `bool`/`int` fields: every partial update overwrites the omitted fields with zero values.
- A new call site passes `(orgId, userId)` to `(userId, orgId)`, both `string`, so the permission check runs against the wrong tenant.
- A new endpoint returns the ORM `User` entity, which now serialises `passwordHash` (report with `category: "security"`).

**`yellow`** — real, but it fails safely, sits on a rare path, or the damage is cosmetic or internal.
- The new `'refunded'` status falls into `default` in an existing label formatter and renders as "Unknown"; no data is harmed.
- A new `update()` skips the `start <= end` check the constructor enforces; a report shows a negative duration but nothing persisted depends on it.
- A getter returns the internal list and a caller added in this change sorts it in place, reordering what the owner displays.
- A bare `# type: ignore` hides a real `Optional` mismatch that raises a clear `AttributeError` on an uncommon input.

**Below the bar** — representable illegal states with no producer; missing branded ids or newtypes without a mix-up; "prefer readonly/final/frozen"; `any` in glue code; anemic models, too many responsibilities, type naming; "refactor this to a discriminated union". Leave these out of `notes` as well: `notes` is shown to the author as this lens's green-light line, and a design opinion there reads as a finding that skipped verification.

## Cheapest proof

`test_idea` is for the verifier to run; you stay read-only. Searches are the exception: run them yourself and quote the hits in `evidence`. A good `test_idea` builds the illegal value through the public path and makes one assertion on the victim. One input, one assertion, and name the existing test file it would slot into when there is an obvious one.

- **Construction**: "`new DateRange(a, b).withEnd(beforeA)` should throw; currently returns a range whose `days()` is negative."
- **Boundary**: send the smallest payload that is legal on the wire but illegal for the type — "`POST /webhook {"id":"x"}` (no `amount`) should return 400; currently 200 and a ledger row with NULL amount."
- **Aliasing**: "`const xs = cart.items(); xs.push(item);` then `cart.total()` should be unchanged", or "`A().tags.append(1); assert B().tags == []`".
- **Unhandled variant**: call the existing formatter/handler with the new value and assert it does not take the default branch.
- **Argument swap**: call through the new call site with distinguishable values (`user='u1'`, `org='o1'`) and assert which one the callee receives.
- **Round trip**: serialise then deserialise and compare — an id of `9007199254740993` through the JSON client, or an old cached payload decoded with the renamed field.
- **Static proof when nothing needs to run**: a search that lists construction sites bypassing the factory (`rg "Money\{" -g '!money.go'`), or a three-line snippet that builds the illegal instance and still type-checks. "Compiles but should not" proves the hole; pair it with the victim line so it also proves the harm.
