# Lens: API Contract & Backward Compatibility

## Mission

Protect everyone who depends on this code without being in the diff: HTTP/RPC clients, library users, other services reading the same queue or table, deploy manifests that set env vars, scripts that parse CLI output. These breaks compile, pass the author's tests, and fail somewhere else after release — often in a system the author cannot see. A finding from this lens names the contract that changed, the consumer that depends on the old behaviour, and the missing shim or version step that would make the change safe. Set `category` to `api-compat`.

## Where to look first

- **Read the removed lines.** Unlike most lenses, the defect here is usually in what was deleted or renamed. For every `-` line on a surface file, ask "who still expects this?".
- **Anchoring a removal.** Anchor on the added or modified line that replaces the old contract (the renamed declaration, the new default, the new validator). A hunk that only deletes has no such line: use an added line within a few lines of the deletion if there is one, otherwise the surviving line directly next to the deletion in the new file — it sits inside the diff hunk, so a comment can still attach there. Copy that line into `anchor` and quote the removed line in `evidence`. For a deleted file, anchor on a changed line that belongs to the same removal (entry point, route table, spec) and name the deleted path in `body`.
- **Surface files get the attention:** route tables and controllers; request/response DTOs, serializers, schemas; package entry points (`index.ts`, `package.json` `exports`, `__init__.py`/`__all__`, `lib.rs` `pub` items, exported Go identifiers, `public` Java/C# types); `.proto`, `.graphql`, `openapi.*`, `.avsc`, JSON Schema; CLI definitions (argparse/click, cobra, clap, commander); config loaders and env reads; event/message producers and consumers; migrations on tables another service reads; webhook payload builders.
- **Skim:** code that is unreachable from outside its package (`internal/`, `_underscore` modules, `pub(crate)`, package-private, non-exported), tests, and purely additive changes — with one exception: additions to *outputs* (new enum value, new event type) deserve a look for strict consumers.
- **Read the brief early.** "Behaviour changes" tells you which breaks are declared. "Claims to check" often holds "backwards compatible" or "no API change" — exactly the claims this lens exists to test. A declared break is not a defect in itself; an incompletely executed one is (Confirm step 6).

## What to hunt for

- **Removed or renamed public name with no alias** — export, route (path, HTTP method, prefix, path-param name), field, query param, header, CLI flag, env var, config key. The old name keeps working nowhere and the consumer gets a 404/405, `ImportError`, "unknown flag", or a silently ignored setting. Confirm: search the whole repo for the old name, including string forms and case variants (`user_id`, `userId`, `USER_ID`), in other workspace packages, generated clients, docs, examples, Dockerfiles, compose/helm/terraform, CI workflows, `.env.example`.
- **Signature changes on exported callables** — new required parameter, reordered positionals, narrowed input type, widened return (now nullable/`Optional`/union). In Python and JS a positional reorder binds the wrong arguments without any error. Adding a method to an exported Go interface or a Rust trait without a default breaks every external implementer; adding a field to a Rust `pub struct` or a variant to a `pub enum` lacking `#[non_exhaustive]` breaks constructors and matches; Kotlin default params and C# optional params are compiled into call sites, so binary consumers break even when source compiles. Confirm: open the entry point to prove the symbol is exported, then find callers outside the compile unit.
- **Response shape changes** — field removed, renamed, retyped (int id → string, scalar → array, object → id), or nullability flipped. Look beyond the DTO: a serializer-wide setting changes every payload at once (`JsonNamingPolicy`, pydantic `alias_generator`, serde `rename_all`, Jackson naming strategy), and null-vs-absent flips through `omitempty`, `exclude_none`, `JsonInclude.NON_NULL`. Confirm: trace from the changed line to the bytes on the wire, then open a consumer that reads the field.
- **Request validation tightened** — newly required field, smaller max, stricter pattern, unknown fields now rejected (`extra="forbid"`, `DisallowUnknownFields()`, `additionalProperties: false`). Requests that succeeded yesterday now get 400/422. Confirm: find an existing client, fixture, or documented example that would now be rejected.
- **Status code and error contract changes** — 200→204, 404→403, 400→422, error body `{error}`→`{errors:[…]}`, renamed machine-readable error codes; in libraries, a different exception class or a Go sentinel error no longer matched by `errors.Is`. Clients branch on these. Confirm: search consumers for the old code/class/string (`status === 404`, `except OldError`, `errors.Is(err, ErrX)`).
- **Changed default or semantics under an unchanged signature** — page size, sort order, timeout, inclusive→exclusive bound, seconds→milliseconds, UTC→local, case sensitivity, sync→async (now returns 202). Nothing fails to compile, so this is the break most likely to ship. Confirm: find a caller that omits the argument or relies on the old behaviour, or a doc/spec line that states the old default. Without one of those it is a product decision, not a finding.
- **Wire-format violations** — proto field number reused or retyped, field removed without `reserved`, enum values renumbered, field moved into a `oneof`; Avro/JSON Schema field added without a default; enum string values or date formats changed. Old binaries misdecode rather than fail. Confirm: `git log -p -- <schema file>` to see what the number/name meant before, and whether the schema was ever released.
- **Output enum/union growth with strict consumers** — a new status value, event type, or variant reaching a consumer that switches exhaustively or deserialises strictly (Java `Enum.valueOf`, serde without `#[serde(other)]`, TS `assertNever`, a spec that declares a closed `enum`). Confirm by opening such a consumer or the spec; without one this is below the bar.
- **Schema shared with a separately deployed component** — event and queue payloads, webhook bodies, JWT claims, and tables, views or columns that another service, worker, ETL job or reporting query reads. Producer and consumer ship at different times, so each must tolerate the other's shape. Confirm: open the other side (sibling service dir, consumer group, SQL in another package) and show the exact read that fails — a missing key that throws, a dropped column in a `SELECT`. Skew between two versions of the *same* deployable (own cache, own sessions, own tables during a rolling deploy) belongs to the `data-migrations` lens; do not hunt for it here.
- **Spec and handler out of sync** — handler changed but OpenAPI/GraphQL SDL/proto/generated client did not, or the reverse. GraphQL specifics: output non-null→nullable and input nullable→non-null are both breaking; field removed with no prior `@deprecated`. Confirm: open the spec entry for that operation and compare field by field; then check whether the spec is generated in CI (if so, there is no drift to report).
- **CLI, env and config contracts** — short flag reassigned, exit code changed, stdout format changed where scripts parse it (`--json`, porcelain modes), env var renamed with no fallback read of the old name, config key moved with no migration so the old key is silently ignored and the default applies, or a newly *required* env var/config key with no default so existing deployments fail to boot. Confirm: read the loader to see what it still honours and what happens when the value is absent; search manifests, compose/helm files, CI and scripts in the repo for the old spelling or for the missing new one.
- **Behavioural contracts clients lean on** — result ordering, pagination style (offset→cursor), idempotency of a retried call, webhook payload/signature scheme, required auth scope, and for plugin/hook APIs the order and arguments with which user callbacks are invoked. Confirm: find the doc, test name, or consumer code that encodes the old promise.
- **Packaging contract of a published library** — an `exports` map added or narrowed so deep imports (`pkg/lib/x`) stop resolving, `main`/`types`/`bin` entry removed or repointed, CommonJS→ESM switch (`"type": "module"`), raised runtime floor (`engines`, `requires-python`, Rust `rust-version`, `go` directive, target framework), peer-dependency major bump. Consumers break on install or import without any code of theirs changing. Confirm: the package is published, and the version bump in this change (or the changelog) is not a major.
- **Missing deprecation or version step where the project has a policy** — in-place change to `/v1/` while `/v2/` exists, removal of a symbol that was never marked deprecated in a project that otherwise deprecates first, breaking change in a published library without the major bump or changelog entry its own history shows it uses. Confirm: read CHANGELOG, version file, and how the last removal was handled. No visible policy → no finding.

## Confirm before you report

1. **Prove the surface is public.** Show the path from the changed line to the outside: exported from the package entry point, mounted on a router, present in a spec or docs, read from the environment, written to a queue/table another component reads. Cite that file:line. If you cannot, stop here.
2. **State the contract delta exactly.** Reconstruct the old behaviour from the removed lines or `git show <base>:<path>` and write "before: X / after: Y" with concrete values. Vague deltas ("response changed") get refuted.
3. **Find the consumers and classify them.** (a) In-repo consumer not updated — cite its file:line; this is the strongest finding. (b) External consumers evidenced — the package is published (`package.json` without `private`, `publishConfig`, PyPI/crates metadata, release tags), or the API is documented for third parties, has an SDK, or is versioned. (c) No evidence of any consumer beyond the code updated in this change — drop it.
4. **Tie every search hit to this surface.** A grep for `status` or `user_id` matches unrelated columns, locals and other endpoints. Open each hit you intend to cite and show it reads *this* endpoint, import, message or variable — follow the URL, the import path, the topic name. Hits in the change's own removed lines, in CHANGELOG history, or in comments are not consumers.
5. **Look for the shim.** Search the new code for the old name: alias, re-export, deprecated wrapper, fallback env read, serializer emitting both fields, versioned route left intact, default value for the new parameter, tolerant reader. Also check mapping layers — an internal rename behind an unchanged `json:"…"` tag, `@JsonProperty`, or `Field(alias=…)` never reaches the wire.
6. **Check intent and completeness.** If the brief, PR text, or CHANGELOG declares the break and the follow-through is complete (consumers, spec, version, migration), drop it. If declared but incomplete, report the specific gap, not the decision.
7. **Check a compiler does not already connect the two sides.** If every affected consumer is built and type-checked together with the change, CI reports the break and you add nothing. This lens earns its keep where nothing links producer and consumer: wire formats, string-keyed access, dynamic languages, config/env, separately deployed or separately released consumers.
8. **One contract change, one finding.** A rename that strands five consumers is a single finding that lists all five in `evidence`, not five findings. This keeps the verifier's work proportional and leaves room under the findings cap for distinct breaks.
9. **Write the scenario as consumer + action + before/after.** Example: "`web/src/api/orders.ts:44` reads `res.user_id`; after this change the handler emits `userId`, so the orders page renders `undefined`." Put every place you checked for a shim in `evidence`. For `self_confidence`: class (a) with the stale consumer cited, or a violated released spec, supports 80 or more; class (b) inferred from publication alone sits around 40-60.

## False positives specific to this lens

- **Internal symbols that look public.** A `public`/exported keyword is not an API. Check the entry point, `exports` map, `__all__`, `internal/` placement, `@internal`/`@VisibleForTesting` markers before treating a rename as breaking.
- **Surface born in this change or never released.** Compare against the last release tag or the CHANGELOG "Unreleased" section; anything added since then, or in this same diff, has no consumers to break. Same for names marked experimental, beta, `unstable_`, or gated behind a flag that is off.
- **Additive changes.** New endpoint, new optional request field, new optional parameter with a default, new response field — safe unless you have opened a strict consumer that rejects it.
- **Generated files.** Do not flag churn in generated clients or specs; find the source. Do not flag "spec not updated" when a CI step regenerates it.
- **Monolith with all callers updated.** If the only consumers live in this repo, ship in the same deployable, and were updated in this change, there is no break. Still check for separately shipped consumers (mobile app, cached SPA bundle, worker on its own release cadence).
- **Stale prose on its own.** A README or guide that still shows the old flag or field is evidence of what the contract was — use it in step 3 — but "docs not updated" by itself is the `docs-comments` lens's call, not a compatibility break.
- **0.x or explicitly unstable libraries.** Where the project states no stability guarantee, a break is allowed; the most you may have is a missing changelog note, and only if the project keeps one.
- **Bug fixes toward the documented contract.** If docs or spec always promised X and the code now does X, that is not a break — unless you find an in-repo consumer that depends on the old buggy behaviour.
- **Test, fixture, mock-server and dev-tooling surfaces.** Flags of internal scripts and shapes of test helpers are not contracts unless other repos' docs point at them.

## Severity guide

`red` — a consumer you can name, or any client following the released spec/docs, gets an error or misreads data on a realistic path, and no shim exists:
- JSON field renamed `user_id`→`userId` while `mobile/` and `openapi.yaml` still use `user_id`.
- Proto field number 4 reused with a different type; older binaries and stored messages decode garbage.
- `DATABASE_URL` renamed to `DB_URL` with no fallback while `deploy/helm/values.yaml` still sets the old name, so the service boots against the default.
- The billing worker (separate deployable) now requires a payload field that the unchanged API producer never sets — every message is rejected.

`yellow` — a real contract change whose blast radius is limited, loud-and-safe, or evidenced only by publication:
- Exported function removed from a published library with no in-repo users and no major bump or deprecation, where project history shows both are customary.
- OpenAPI still documents a query parameter the handler no longer reads (hand-maintained spec).
- Default page size 50→20 on a documented endpoint whose clients follow `next` links; docs still say 50.
- A cross-service reader that fails only on rollback, or only for messages in flight during the deploy window, and retries or dead-letters them safely.

Below the bar: additive changes, internal renames, "some unknown client might depend on this" with no published surface, "consider versioning this API", missing changelog in a project that keeps none.

## Cheapest proof

`test_idea` is a recipe for the verifier, who may run code; you may not, so use only search and `git` to build your own evidence. The ideal recipe passes on the base commit and fails on the head commit, and says so. Prefer, in order:
- **A search that shows the stale consumer:** `git grep -n "user_id" -- mobile/ openapi/` still matches after the rename.
- **An old-usage snippet against head:** three lines written against the base API — import the removed name, call with the old positional order, run `tool --old-flag`, boot with only the old env var set — expecting success, currently failing or returning a different value.
- **A shape assertion:** serialise one fixture through the real serializer/handler and assert the old key, type, status code, or error code; or diff the key sets between base and head.
- **A cross-version decode:** feed a payload or fixture produced by base code into the head reader, and the reverse for rollback safety.
- **A schema differ where the repo already has the schema:** `buf breaking --against '.git#branch=<base>'`, `oasdiff breaking`, `graphql-inspector diff`, `cargo semver-checks`, `apidiff`, `japicmp`, `griffe check`, api-extractor report diff. Name the two files or refs to compare.
